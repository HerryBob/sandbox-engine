# 未来方向：四条线程拆分为独立类

> **状态**：未实现，仅定方向（2026-11-13 讨论定案）
> **前置**：先有 headless 帧循环冒烟（见 `docs/通读记录/STATE_OF_CODE.md` 的 T1）
> **结论**：方向对，**但现在不改**——理由见第六节

---

## 一、现状

`main.cpp`（359–502 行）里四条轨都是就地 lambda：

```cpp
core::ThreadLoop businessLoop("business");
businessLoop.start([&] {
    auto next = std::chrono::steady_clock::now();
    while (!businessLoop.shouldStop()) {
        /* 58 行业务 tick */
        next += std::chrono::milliseconds(40);
        std::this_thread::sleep_until(next);
    }
});
```

四条的规模：业务 58 行、物理 13 行、输入 6 行、渲染 50 行。

**写法上的三个问题**（都不是性能问题）：

1. `[&]` 隐式捕获十几个外部变量 —— 读的时候看不出这条线程依赖谁
2. body 里混了三种职责（推进 / 驱动流式 / 收发桥），渲染轨前 40 行其实是"队列泵"，不是线程逻辑
3. 四种节拍策略（绝对时刻 / 测量 dt / 固定 sleep / vsync 阻塞）散在 body 里，只能靠注释区分

## 二、目标形态：**每线程一个类，不是一个大的 Runtime 类**

```cpp
// 只拥有本线程的节奏与统计；共享对象一律引用，绝不拷贝
class BusinessThread {
public:
    BusinessThread(BusinessWorld& world, ChunkStreamer& streamer,
                   core::TimeManager& tm, shared::CameraState& cam,
                   shared::PlayerInput& in, PhysicsBridge& bridge);

    void run(core::ThreadLoop& loop);   // 唯一入口，内含 while

private:
    void tick();                        // 纯业务，可单测
    void pace();                        // 节奏独立出来

    // 本线程独占的可变状态 —— 与其他线程的字段不同对象，天然不假共享
    std::size_t reportCounter_ = 0;
    bool demoPackQueued_ = false;

    BusinessWorld& world_;  ChunkStreamer& streamer_;  // 全部引用，非拥有
    core::TimeManager& tm_;  shared::CameraState& cam_;  /* ... */
};
```

`run()` 只留 5 行：

```cpp
void BusinessThread::run(core::ThreadLoop& loop) {
    auto next = std::chrono::steady_clock::now();
    while (!loop.shouldStop()) {
        tick();
        pace();                       // 内部：next += 40ms; sleep_until(next);
    }
}
```

四条轨各一个类：`BusinessThread` / `PhysicsThread` / `InputThread` / `RenderThread`。

## 三、为什么是"每线程一个类"而不是"一个 EngineRuntime"

| 方案 | 问题 |
|---|---|
| **一个大的 `Runtime`** | 四条线程共享**全部成员** → 某条线程顺手碰了别人的字段，编译器不报、运行时是数据竞争。现在的 `[&]` 反而更安全：每条 lambda 只捕获它用到的。**类会放大意外共享面** |
| **一个大的 `Runtime`** | 项目里已经有 2240 行的 `VulkanContext`。再来一个"什么都有"的类，等于把 `main.cpp` 的问题搬到另一个文件 |
| **每线程一个类** | 可变状态物理隔离在各自对象里，正好对应"四轨互不共享"的架构原则 |

## 四、性能：**不是考量因素**

| 层 | lambda 现状 | 类写法 | 差异 |
|---|---|---|---|
| 线程启动 | `[&]` 捕获十几个引用 → 超 SBO → 一次堆分配 | `[this]` → 8 字节，走 SBO，无分配 | 一次性，几百纳秒 |
| 每轮循环 | `while` 在 lambda **内部**，`std::function::operator()` 只被调用 **1 次** | `this->tick()` 直接调用 | **0** |
| 每 tick 工作 | 全在 `World`/`PhysicsWorld`/`VulkanContext` | 相同 | **0** |

**唯一要记住的规则是假共享**：跨线程频繁写的计数器不能挤在同一条 64B cache line 上（必要时 `alignas(64)`）。但本项目四条轨合计每秒几百次迭代，抢缓存行的成本是**每秒微秒级** —— 不构成理由。

> 结论：性能既不会变好也不会变差，别拿它当决策依据。

## 五、收益与代价

### 收益

| 收益 | 能否兑现 |
|---|---|
| **可观测性**：profiler/栈回溯里是 `BusinessThread::tick` 而不是 `<lambda_1>` | ✅ 立刻 |
| **可测**：`tick()` 可同步调用、喂假数据 | ⚠️ 需要依赖注入边界 + fake，是比"改类"更大的工程 |
| **节奏抽象**：`Pacer` 成为类型，四种策略第一次可以并排对比 | ✅ |
| **`main.cpp` 瘦身**：599 → 约 250 行 | ✅（搬走，不是消除） |

### 代价

| 代价 | 说明 |
|---|---|
| 成员初始化顺序成为新的隐式依赖 | "捕获顺序"换成"声明顺序"，问题没消失只是换形式 |
| 析构顺序 | 线程必须在成员死之前 join → 靠析构函数体里的 `stop()` 兜住，又一条位置敏感约定 |
| 需要定义依赖注入边界 | 否则"可测"只是纸面收益 |

## 六、为什么现在不改

1. **没有测试保护**。T1（headless 冒烟）还没做，重排线程装配等于把唯一能跑的东西拆开重装。
2. **可测性暂时兑现不了**。`tick()` 要喂假 `World`/假 `VulkanContext` 才测得动。
3. **不改也没漏 bug**。除了"lambda 里没有 try/catch、异常直接 `std::terminate`"，四条 lambda 没产生过事故。

---

## 七、迁移顺序（将来照做）

```
T1 headless 冒烟（100 帧 drawFrame）
  → Pacer：把四种节奏统一成一个小类型（3 行改动，收益 80%）
  → 每线程一个类（BusinessThread / PhysicsThread / InputThread / RenderThread）
  → （可选）线程 body 抽到独立 TU，main.cpp 只剩装配
```

顺带一起做的两个小修（独立于本方向）：

- **业务轨加追赶上限**：`if (next < now - 200ms) next = now;` —— 现在是无上限追赶，与物理轨的 `kMaxStepsPerFrame=5` 不对称
- **线程函数加异常边界**：`ThreadLoop::start` 的 lambda 里包 try/catch，至少把异常打进日志再终止

## 九、明确不做的事

- ❌ 不引入虚基类 / 抽象接口 —— 四条轨没有运行时多态需求，虚函数只会妨碍内联
- ❌ 不做 `EngineRuntime` 大对象
- ❌ 不改节奏策略本身（除业务轨追赶上限）
- ❌ 不在没有冒烟测试时动 `drawFrame` 相关代码
