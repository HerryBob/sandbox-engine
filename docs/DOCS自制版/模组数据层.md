# 模组数据层

> **状态**：设计设想，**当前不实现**。模组 API 尚未设计完毕，本文只记录分层思路与边界判断，不含格式定义、字段定义或加载流程。
> **关系**：本文是《模组资源与数据处理.md》的**上位概念**，不取代它。已实现的 assets/data 两段式，是本文所说"数据层"的一部分（外观资产与脚本数据），不是全部。

## 一、为什么要分两层

原生 DLL 模组有一个绕不开的代价：**代码模组是平台相关的**。Windows 的 `.dll`、Linux 的 `.so`、macOS 的 `.dylib`，各自编译一份。

如果所有模组都必须写代码，那么这个代价会落到每一个模组作者身上。但实际情况是：**大多数模组并不需要代码**——它们只是"加一个方块、加一个配方、加一种生物、改一下掉落"。

这部分内容如果做成数据，就同时得到三个好处：

1. **跨平台**：一份数据，三个平台通用，不需要编译
2. **可静态校验**：错误在加载期暴露，而不是运行时崩溃
3. **可被 AI 生成**：结构化描述比 C++ 代码可靠得多

所以分层的目的，与"让开发更简单"关系不大，本质是**把平台相关的成本集中到少数真正需要代码的模组上**。

## 二、两层的边界

判定规则只有一条：**是否需要每帧读写世界**。

| 层 | 内容 | 跨平台 | 需要编译 | 谁来写 |
|---|---|---|---|---|
| **数据层** | 方块与物品定义、材质、模型、配方、掉落、生物属性、语言、音效、世界生成参数、演示场景 | 是 | 否 | 人、AI |
| **代码层** | 自定义行为、物理交互、渲染管线、网络协议、跨模组的运行时逻辑 | 否 | 是 | 人 |

边界不是"能不能序列化"，而是"要不要和世界实时交互"。一个方块的颜色可以序列化，但它每帧检查相邻方块并改状态的逻辑不能——前者归数据，后者归代码。

## 三、数据层包含什么

按内容类别分，不按文件类型分：

- **定义类**：方块、物品、生物类型、方块实体类型
- **参数类**：硬度、爆炸抗性、摩擦、密度、浮力系数、受风面积
- **规则类**：配方、加工、掉落表、燃烧值、燃料值
- **外观类**：材质、模型、动画、音效、粒子
- **世界类**：群系参数、地形噪声、矿物分布、结构模板
- **文本类**：名称、描述、提示
- **教学类**：演示场景（放下方块即可播放的实物演示）

后三类里的"教学类"，是本文新提出的一项：演示场景本身也应当是可序列化的数据，而非硬编码在代码里。

## 四、与已实现资源系统的关系

已经落地的 assets/data 两段式，对应数据层的一部分：

| 已实现 | 归属 |
|---|---|
| `assets/textures/`、`assets/models/` | 数据层·外观类 |
| `data/worldgen/noise/`、`data/worldgen/presets/` | 数据层·世界类 |
| `DataRegistry<T>` 全量注册 | 数据层的加载机制雏形 |

尚未纳入的：方块定义、配方、掉落、生物属性、演示场景。这些目前仍在代码里硬编码，属于"将来要搬进数据层"的部分。

**不需要推翻现有实现。** 现有系统已经具备三件事：统一收集（路径索引）、按域解码（各子系统自解）、全量注册。数据层只是把更多内容接进这套流程。

## 五、数据层必须满足的性质

1. **平台无关**：不含指针、不含字节序假设、不含平台特定路径
2. **可校验**：字段缺失、类型不符、引用不存在，都在加载期报出，不拖到运行时
3. **可合并**：多个模组的数据能共存，冲突有明确规则
4. **可枚举**：加载完成后能列出全部条目，而不是"用到才查"
5. **可审查**：不执行代码，安全边界清楚
6. **可被 AI 生成**：结构固定、字段明确、有反例可对照

前五条是工程性质，第六条是本文分层的另一个动机。

## 六、冲突与合并

现有实现采用"引擎先、模组先到先得、后到记警告"，这在数据层扩展后会不够用。数据层的条目数量比资源多一个量级，冲突会从"偶尔"变成"常态"。

将来至少需要：

- **命名空间**：每个模组的条目带来源前缀，避免同名
- **覆盖策略**：追加、覆盖、补丁，三种语义分开，不能混成一种
- **冻结时机**：注册表何时关闭，关闭后写入必须失败（这条已在现有注册表机制里成立，需要延伸到数据层）

以上三条都**不在本文定案**，只是记录为 API 设计时必须回答的问题。

## 七、与 AI 的关系

数据层是"AI 能可靠生成"的那一部分，原因有三个：

- 结构固定：字段和类型都有明确约束，AI 不需要猜
- 可校验：生成错了，加载器会报出来，不会静默生效
- 无副作用：数据不执行代码，生成错误最坏的结果是"这个方块没出现"，不是"进程崩溃"

配套需要的是：字段说明、每个字段的取值约束、常见错误的反例。这正好接上"面向 AI 的模组文档"那条思路——**AI 文档的重点不是教它怎么写，而是告诉它哪些写法会被拒绝**。

## 八、明确不做的事

**数据层不能退化成脚本语言。**

一旦为了"更灵活"加入条件判断、表达式、函数调用、变量引用，它就变成了代码层，同时失去：

- 跨平台（脚本引擎本身要跨平台）
- 可静态校验（动态求值校验不了）
- 可审查（又变回"执行未知代码"）

这是本文最重要的一条红线。**灵活性应当由"更多的字段组合"提供，而不是由"更自由的语法"提供。**

如果某一类内容确实需要条件逻辑，正确做法是把它归到代码层，而不是给数据层加语法。

## 九、待定（API 设计完毕后补）

- 格式选型：JSON、自定义文本、二进制
- 加载顺序与依赖声明（模组 A 的数据引用模组 B 的条目，谁先加载）
- 版本号与兼容规则（数据结构变更后，旧数据怎么处理）
- 覆盖优先级的具体规则
- 是否支持热重载
- 数据层与代码层之间的引用形式（句柄、字符串标识、整数编号）
- 演示场景的数据结构
