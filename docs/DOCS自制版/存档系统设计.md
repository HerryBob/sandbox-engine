# 存档系统设计（原型，2026-11-26）

> 目标：**原型可用**，不是最终形态。明确写了「本原型不做」的清单，避免范围膨胀。
> 定位：LOD / 切世界 / 多人的**共同前置** —— 它定义"chunk 是什么身份、怎么落盘、怎么确定性重建"。

---

## 0. 一句话设计

**存全量体素 + 分段表（section table）**：每个 16³ chunk 一个自描述二进制块，
头部固定、正文按 tag-length-value 分段。体素是唯一真值，LOD 与网格**永不入库**。

---

## 1. 为什么这样定（与 LOD 的耦合）

| 问题 | 决定 | 原因 |
|---|---|---|
| 存体素还是存"种子 + 改动 diff" | **存全量体素** | 体素是唯一真值。LOD 采样、物理、生成后续内容都要完整数据；diff 方案要求生成器**跨版本永不改算法**，做不到 |
| LOD 数据要不要入库 | **不入库** | LOD 网格是渲染派生物，依赖渲染器实现细节（分块方式、缩放策略）。入库等于把渲染细节焊死进存档格式。LOD 每次加载时由体素重建 |
| 每个 chunk 一个文件，还是 region 合并 | **原型单文件**；格式预留可分块搬移 | 见 §2 的"自描述"：正文按段切分且带长度，将来合并进 region 文件只是把整块 payload 顺序拼起来，不需重新解析 |
| chunk 身份 | **坐标 + 格式版本 + 生成器版本** | 格式版本不符 → 拒读（重新生成）；生成器版本不符 → 记账告警但**仍读旧数据**（旧地形保留，新生成用新算法，边界靠"已存即真"维持一致） |
| 高度图/列摘要要不要一起存 | **本原型不存**，但段表允许将来加 | 高度图是 LOD/生成优化的派生物，可由体素即时算出（16³ 扫描很便宜）。真需要时加一个新 tag 即可，格式版本不必升 |

**核心原则**：**存档存"世界的真值"，不存"任何派生物"**。凡是能由体素确定性算出来的（网格、LOD、高度图、光照占位），都不落盘。

## 2. 二进制格式

### 2.1 文件布局

```
chunks/<x>.<y>.<z>.bin

┌──────────────────────────────────────────────┐  ← 固定 32 字节头
│ magic        "CHNK"            4B            │
│ formatVer    u16               2B            │  格式版本（本原型 = 1）
│ headerSize   u16               2B            │  头长（给未来扩容留的，本版 = 32）
│ genVer       u32               4B            │  生成器版本（地形算法版本）
│ chunkX       i32               4B            │  chunk 坐标（与文件名互为校验）
│ chunkY       i32               4B            │
│ chunkZ       i32               4B            │
│ sectionCount u16               2B            │  段数（本原型 = 2：palette + indices）
│ flags        u16               2B            │  bit0 = 全空气（正文为空）
│ checksum     u32               4B            │  正文 FNV-1a 32（防截断/写入中断）
├──────────────────────────────────────────────┤
│ 段表 sectionCount × 8B                       │
│   tag   u16                                  │
│   len   u32                                  │
│   pad   u16                                  │
├──────────────────────────────────────────────┤
│ 段正文（按段表顺序紧跟）                       │
└──────────────────────────────────────────────┘
```

**为什么是"段表"而不是固定字段**：将来加 LOD 摘要、光照占位、生物存档、方块实体，
都只是新增一个 tag，**老版本读到未知 tag 直接跳过**（len 已知），不需要升 formatVer。
这是"现在不做空壳、将来零成本扩展"的做法。

### 2.2 段的定义（本原型只写两个）

| tag | 名称 | 内容 |
|---|---|---|
| `0x0001` | `Palette` | `count u16` + `count × u16`（方块类型 id，下标即调色板索引）|
| `0x0002` | `Indices` | `bits u8` + `pad u8` + `dataLen u32` + `data[dataLen]` |

- `bits ∈ {4, 8, 16}`，与内存布局**逐位一致**（4 位：一字节两格，低半字节在前；8 位：一字节一格；16 位：小端 u16 一格）。
  这样存/取都不需要重新打包，是"零转换"的关键。
- `bits` 由 `ChunkData::chunkIndexBits()` 给出，`dataLen = 4096 × bits / 8`。

### 2.3 依赖顺序与校验

读入时必须按顺序验证：

```
① magic / formatVer / headerSize      → 不符 = 拒读（当"无存档"处理，重新生成）
② 文件名与头里的 chunkX/Y/Z 一致       → 不符 = 拒读（防止文件放错目录）
③ sectionCount × 8 + headerSize ≤ 文件长度，且每段 len 不越界
④ checksum 与正文比对                 → 不符 = 拒读并记日志（截断/损坏）
⑤ genVer 与本进程不同                 → 记 WARN 但**继续读**
```

**任何一步失败都必须返回"无此 chunk"**，让流式走生成路径 —— 存档坏了不能让世界加载卡死。

## 3. 加载与写盘路径（接现有流式）

```
流式请求某列 (x,z)
   ├─ 对每层 y：磁盘有 <x>.<y>.<z>.bin？
   │    ├─ 有 → 读盘 → 校验 → World::applyGeneratedChunk（走同一条写入路径）
   │    └─ 无 → 生成 → 写入 World → 标记"待写盘"
   │
写盘时机（原型）
   ├─ chunk 卸载时立刻写（世界回收上限附近，量小）
   └─ 退出时写所有待写 chunk
```

**为什么加载也走 `applyGeneratedChunk`**：让"来自磁盘"和"来自生成"共用一条写入路径
（同样标脏、同样通知渲染、同样重建物理）—— 少一条分支就少一类不一致。

---

## 4. 本原型不做（明确清单）

| 不做 | 原因 / 何时做 |
|---|---|
| 异步 IO、写盘预算 | 量小（81 chunk ≈ 170KB），同步足够；等 region 合并时一起做 |
| 压缩（RLE/zstd） | 先量原始体积。4 位索引本身已压到 1/8 |
| region 分区（32×32×32 chunk 一文件） | 段表已为"整块搬移"铺好路，等 chunk 上千再合并 |
| 崩溃一致性（fsync / 临时文件 + 原子替换） | 原型用"checksum + 拒读"兜底，不做事务 |
| 版本迁移 | 格式版本不符就重新生成 |
| 世界选择界面 | 固定 `saves/world/` |

---

## 5. 验收

- **自检**：`ChunkData` 序列化 round-trip（全空 / 单材质 4 位 / 多材质 8 位 / 超过 15 种材质 16 位），逐格比对 + `paletteSize`/`bits`/`dirty` 一致。
- **手动**：放方块 → 退出 → 重开 → 方块还在；删 `saves/` → 重开 → 回到原始地形。

---

## 6. 与 LOD 的后续衔接（记录，不在本原型实现）

1. LOD 需要"跨 chunk 的连续采样" → region 文件（顺序 IO 友好）是必然的一步，段表已支持。
2. LOD 需要"同一 chunk 出现在多个层级" → 层级是**渲染期**概念，不落盘；加载时按视距生成所需层级。
3. LOD 需要"低层级快速加载" → 若将来生成成本变高，可加 `tag 0x0003 ColumnHeights` 段
   （每列最高非空气方块 y），让远端只读这一小段。**这就是段表预留的真正用途。**

### 实现时改掉的三处设计（文档已同步）

1. **写入时规范化调色板**：原设计是"逐字节搬内存"，但内存里 palette 顺序取决于方块写入先后
   → 同一世界存两次字节可能不同（实测：加载后重存有 2 个 chunk 的字节变了）。
   改为写入时按类型 id 排序 + 重映射索引，**存档字节只取决于世界内容**，可以用来做存档 diff。
   代价：写盘时一次 4096 遍历（只在写盘发生）。
2. **空 chunk 必须写**：原设计"空 chunk 不建、不写"，但加载端要求"一列 4 层齐全"，
   缺层的列永远 miss → 每次重新生成。改为空 chunk 也写 32 字节的头。
3. **存档根目录**：原设计相对工作目录（会落在 `build/Debug`，clean build 连档一起删）。
   改为从 exe 向上找仓库根（有 `.git` 或 `tools` 的那级）→ `<repo>/saves`。
