# 架构决策：渲染层拆分（2026-11-25）

## 起因

`VulkanContext` 在 S1 之前是 **2,326 行 .cpp + 376 行 .hpp**，一个类同时承担九块职责：
设备/交换链、渲染通道/管线、帧基础设施、纹理、方块网格、"刚体网格、实体模型、HUD、每帧录制。

下一步要做 P20（网格重建预算）、光影、三类 LOD（世界/结构/实体）、HUD 模组化 ——
这些都会往这个类里加代码。等到 10k 行再拆，成本是现在的数倍，且回归风险高。

## 决策

**不做大爆炸重构；按"改到哪拆到哪"增量拆分，每次 ≤300 行，每步一个提交。**

新规矩（已写进 AGENTS.md §3 的解释口径）：
- 新功能**不得**直接加进 `VulkanContext`
- 改动碰到某职责时，顺手把那部分抽成独立类
- 不改无关命名、不搬无关文件（避免 diff 噪音）
- 依赖方向严格单向：`Renderer → *Store/*Renderer → DeviceContext`

## 目标结构

```
main
 └─ Renderer（门面，main 调用面不变）
      ├─ DeviceContext        instance/surface/device/queue（句柄所有权唯一出口）
      ├─ SwapchainController  swapchain/重建/帧缓冲 resize
      ├─ FrameInfra           命令池/同步/Uniform/深度·颜色附件
      ├─ PipelineSet          render pass + 主图形管线（+ HUD 管线最终也归它）
      ├─ TextureSet           ★已抽出：图 → view → sampler（GPU 侧）
      ├─ ChunkMeshBuilder     ★纯 CPU：方块快照 → 顶点/索引（可单测、可异步）
      ├─ ChunkMeshStore       每 chunk GPU 缓冲 + 延迟销毁（P14）
      ├─ ChunkMeshScheduler   ★已抽出：脏队列 + 每帧预算（P20）
      ├─ BodyMeshStore        刚体网格上传/销毁 + 位姿直读
      ├─ EntityRenderer       实体模型/骨骼/贴图
      ├─ HudRenderer          ★已抽出：HUD 全套（将来做成 DLL 模组）
      └─ FrameRecorder        每帧录制（pass 列表 → 为光影留位）
```

三条设计约束：
1. `DeviceContext` 独占 Vulkan 句柄所有权；其他类只拿 `VkDevice`/`VkQueue` 的值。
2. Store 只做资源表，Recorder 只做录制（现在 `drawFrame` 既遍历又建命令又管顺序）。
3. `ChunkMeshBuilder` 纯 CPU —— 唯一能单测、能挪进工作线程的部分。

## 纹理 mipmap（2026-11-26）

**通用实现**在 `render/utils/ResourcesUtils`：

```cpp
std::uint32_t mipLevelsFor(w, h);                       // floor(log2(max))+1
bool generateMipmaps(dev, pdev, cmdPool, queue, image,
                     format, w, h, mipLevels);          // vkCmdBlitImage 逐级减半
```

- 用法：`createImage(..., mipLevels, ...)` → 拷贝第 0 级 → `generateMipmaps(...)`
  （入口必须是 `TRANSFER_DST_OPTIMAL`，出口自动转 `SHADER_READ_ONLY_OPTIMAL`）→
  `createImageView(..., mipLevels)`。图像用途要带 `TRANSFER_SRC_BIT`。
- 采样器：**magFilter 保持 NEAREST**（像素风放大要硬边）、minFilter 改 LINEAR + mip 链
  → 远处不闪（摩尔纹消失），近处不变。

| 使用处 | 级数 | maxLod | 备注 |
|---|---|---|---|
| 方块图集（`TextureSet`） | 48² → 6 级 | **限 2 级** | 图集 tile 相邻，高 mip 会跨 tile 渗色；第 2 级每 tile 还剩 ~4px，肉眼可接受 |
| 实体贴图（`EntityRenderer`） | 64² → 7 级 | 全链 | 独立纹理，无渗色问题 |
| 字体图集（`HudRenderer`） | 1 级 | 0 | 屏幕空间固定大小，mipmap 只会让字变糊 |

### 图集改为「每格 1px 间隔 + 边缘挤出」（2026-11-26）

原先图集是**紧挨着**的格子（3×3 × 16px = 48²），UV 精确落在格边界上，于是：

| 现象 | 根因 |
|---|---|
| 方块边缘冒**紫色短线** | UV 落在格边界 → 最近邻/线性过滤取到**隔壁格**的纹素；隔壁若是第 0 格 `default.png`（品红+黑的缺失纹理标记），就是紫线 |
| mipmap 高级别渗色 | 线性缩小必然跨格采样，同理 |

现在：`kAtlasPadding = 1` → 格距 `kAtlasPitch = 18`，图集 3×3 = **54²**。
写入时把图像素铺在格内，再把四条边的像素**挤出**到环绕的 1px 间隔里
（含四角），于是边界上的采样取到的永远是**本格边缘的颜色**。

- `atlasSlotUVPure(grid, size, tile, pad, col, row)` 返回**格内容**（不含间隔）的 UV，
  不做半像素内缩 —— 内缩方案已废弃（间隔方案对 mipmap 同样有效）。
- 有了间隔，图集采样器 `maxLod` 可以放开到完整 mip 链（不再限 2 级）。
- 自检 `selftest::atlasUV()`：1×1..8×8 每格 UV 换算成纹素范围后必须**恰好等于**
  格内容那 16×16 像素（左边界从格内首像素起、右边界到格内末像素止）。
