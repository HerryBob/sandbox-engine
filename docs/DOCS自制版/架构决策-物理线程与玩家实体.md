## 三、物理线程职责边界

**区分标准**：这段逻辑需不需要读本 tick 的 `colliders_` / `bodies_`？

| 候选 | 归属 | 理由 |
|---|---|---|
| 刚体积分 / 碰撞 | 物理线程（已有） | 物理状态的唯一写者 |
| 生物物理（重力、落地、被刚体托着） | 物理线程 | 要读当帧刚体位姿与碰撞体，晚一帧就穿模 |
| 生物 AI（寻路、目标选择） | 业务线程 | 是决策不是求解，且慢，会拖累物理步长 |
| 玩家点击选方块 | 业务线程（已有 DDA） | 是查询，不需要物理状态 |
| 物理交互（压力板被踩、被撞方块破坏） | 物理线程 | 需要"本帧谁压在谁上面" |
| 绳索 / 关节约束 | 物理线程 | 约束求解必须和积分同循环 |
| 存档 / 序列化 | 业务线程 | — |

"交互"要拆开：玩家点击是查询，压力板是物理接触，两者不同线程。

**不拆 `PhysicsWorld` 的触发信号**（现在不拆，YAGNI）：

1. `.cpp` 超过 800 行
2. 出现第二个每 tick 遍历所有实体的循环
3. 两个子系统执行顺序产生依赖

演化方向（到点再说）：`PhysicsWorld` 退回"数据 + 查询"，`RigidBodySystem` / `EntitySystem` / `InteractionSystem` / `ConstraintSystem` 各持引用按固定顺序被调。

## 四、玩家作为第一个生物：当前缺口

### 现状

玩家 = `CameraState`（相机位置 + 朝向），**没有实体**。相机自由飞行，不碰墙、不受重力。

物理侧没有"生物"概念，只有 `bodies_`（刚体，方块集合 + 单 AABB）。

### 缺口（按依赖顺序）

#### 缺口 1：三轴分轴碰撞（硬前提）

`PhysicsWorld.cpp:192-204` 现只回退 x 轴：

```cpp
// 碰撞响应：原型只回退 x 轴（飞船沿 x 运动），速度清零。
// 本帧只响应第一个接触（原型行为保持，断言依赖此回退）。
responded = true;
vxBefore  = b.vx;
nx        = (vxBefore >= 0.0) ? -1 : 1;
if (b.vx >= 0.0)
    b.x = static_cast<double>(ix) - b.centerOffsetX - b.halfExtentX;
else
    b.x = static_cast<double>(ix + 1) - b.centerOffsetX + b.halfExtentX;
b.vx = 0.0;
```

而且当前是"三轴一起积分，再检测一次，只回退一条轴"（`:146-153` 三轴匀速积分）。

生物站立要求 y 轴向下接触地面时**贴回方块顶面并把 `vy` 清零**；水平移动要求 x/z 各自被挡。正确做法是分轴：

```
先移动 x → 检测 → 回退 x 并清零 vx
再移动 y → 检测 → 回退 y 并清零 vy（向下时标记"在地面"）
再移动 z → 检测 → 回退 z 并清零 vz
```

这就是物理引擎里的分轴测试（swept AABB 的简化版）。**这条与你"刚体碰撞暂不做"的决定冲突，但冲突点是刚体不需要、生物需要**——可以把"分轴移动 + 回退"抽成通用函数，刚体按原样只调 x 轴那一分支。

#### 缺口 2：物理侧实体容器

> **最终选择（已实现，见第七节）：不做 `entities_`。**
> 生物作为一种 `MotionType::Kinematic` 的 body 直接放进 `bodies_`——它天然要和刚体、静态碰撞体发生关系，另开容器等于把碰撞检测写两遍，还要再维护一套"刚体 ↔ 生物"的交叉查询。
> 物理引擎里 **body 是容器不是形状**：位置 + 朝向 + 速度 + 运动类型 + N 个 collider。生物的"单 AABB"只是它恰好只有一个 collider，不该让它住进另一个类。
> 以下为当时的原始分析，保留备查。

现在只有 `bodies_`（`RigidBody`：方块数组 + halfExtent/centerOffset）。生物不是方块集合，属性也不同（有意图、有重力、不推动刚体）。

需要在 `PhysicsWorld` 里新增 `entities_`，条目至少含：id、位置、速度、半宽（AABB 半尺寸）、状态（在地面 / 空中）。

与刚体共用碰撞检测函数，但独立容器、独立积分循环。

#### 缺口 3：业务侧玩家实体

> **本轮只完成"相机跟随"这一半（见第八节）**：输入线程读玩家位置，但还没有把移动意图发给物理线程——玩家站着不动。完整闭环见下文。

现在 `InputSampler` 直接改 `CameraState`（自由飞行）。要改成：

```
输入 → 玩家移动意图（WASD → 目标速度方向）
意图 → 物理线程（生物物理）
物理位置 → 业务/渲染
相机 = 玩家位置 + 眼高，视角独立旋转
```

`PlayerInput` 已有结构，需要补"意图速度"字段。

#### 缺口 4：重力与落地

`vy -= g * dt`，落地检测靠缺口 1 的 y 轴回退。第一版只支持站在静态地形上。

#### 缺口 5：相机与玩家分离

> **已实现（见第八节）**：`CameraState` 结构没拆，但玩家模式下位置来源换成了 `PlayerBodyState`，朝向仍归鼠标。一个结构 + 两种位置来源，比分两个结构省事。

#### 缺口 6：跨线程回传

> **已实现一半（见第八节）**：位置走新增的 `PlayerBodyState` 原子槽，不走 `RigidBodyPos` / `BodyPose` 队列——相机跟随要的是低延迟而不是"业务语义"。仍缺"输入上行"（意图 → 物理线程）。

相机跟随时如果要做插值，需要两个快照——现在 `bodyPoseQueue{16}` 够放，但语义上只有"最新"。

## 七、已实现：生物作为 Kinematic body

### 运动类型

```cpp
enum class MotionType { Static, Dynamic, Kinematic };
```

对齐 Rapier 的 `RigidBodyType`（刚体类型）：

| 类型 | 谁 | 行为 |
|---|---|---|
| `Static` | 地形 | 永不移动，在 `colliders_`，当前不进 `bodies_` |
| `Dynamic` | 方块组 | 按力/冲量积分，能挡能被推 |
| `Kinematic` | 生物 / 玩家 | 速度由外部设定，受重力，位置由碰撞修正（MC `Entity.move()` 的做法） |

**物理引擎里 body 是容器不是形状**：位置 + 朝向 + 速度 + 运动类型 + N 个 collider。生物"只有一个碰撞盒"不该让它住进另一个类。

### 玩家体参数

`addPlayerBody(x, y, z)`：

| 字段 | 值 | 说明 |
|---|---|---|
| `motion` | `Kinematic` | 不参与 `contactPairs_` / `CollisionEvent` / `collisions_` 计数 |
| `halfExtentX/Y/Z` | 0.3 / 0.9 / 0.3 | AABB 0.6 × 1.8 × 0.6 |
| `centerOffsetX/Y/Z` | 0 / 0.9 / 0 | `centerOffsetY = 0.9` 让 AABB 底部正好落在基准 y，即**位置锚在脚底中心** |
| `blocks` | 空 | 形状由 halfExtent 直接给，绕过 `recomputeAABB`（后者在 `blocks` 为空时会把 AABB 清零） |

返回分配的刚体 id（`playerBodyId_` 记下来，位置回传时按它认人）。

### 三轴分轴推进

接触集合更新之后、`simTime_` 累加之前：

```
清 onGround → vy -= 9.8 * 0.04 → moveKinematicAxis(1) → (0) → (2)
```

`moveKinematicAxis(RigidBody& b, int axis)`：`delta = v * 0.04`（为 0 直接返回）；先移动再算 AABB 六边界、`floor` 取整；三层循环查 `colliders_`、严格区间重叠；收集"该轴最紧的一格"（正向取最大、负向取最小）；回退：

- 正方向：`pos = best - centerOffset - halfExtent`
- 负方向：`pos = (best + 1) - centerOffset + halfExtent`

回退后清零该轴速度；`axis == 1 && delta < 0` 时 `onGround = true`。

顺序必须是**先竖轴**：否则水平移动会先把身体推进地面，再竖轴回退就变成"贴着地面卡住"。

### 为什么运动学路径不发 CollisionEvent

运动学体是"被外部驱动、只受碰撞修正"的物体，不是碰撞的发起方。让它进 `contactPairs_` 会把"刚体撞到方块"的接触集合语义搅混，`collisions_` 计数也会被每一步落地污染。

**所以日志里的 `碰撞=0` 与"生物是否撞到东西"无关**，是设计选择，不是没撞。

### 验收

```
[物理] sim=1s tick=25 ... 刚体=2 碰撞体=82944 碰撞=0 ... 生物1=(0,4,0) 在地面=1 刚体2=(1.2,0.8,0)
```

### 连带修掉的两处单刚体假设

生物进容器后 `bodies_` 变成 `[生物 id=1, 演示刚体 id=2]`，`front()` 指向生物：

| 位置 | 原写法 | 改法 |
|---|---|---|

## 九、已实现：输入驱动与空格跳跃

### 通道：与相机跟随对称的反向共享槽

```
输入线程（125Hz）──写──> PlayerControlState（vx / vz / jumpRequested）
                                │ 读
物理线程（25 TPS）────── 灌进玩家体 vx/vz + 处理跳跃
```

新增 `src/shared/state/PlayerControlState.hpp`。**没走业务 → 物理的命令队列**：业务线程管方块和区块，不管"玩家按了什么键"；走队列要多两个 tick 的延迟，而操控是 25 TPS 物理 tick 内就该生效的东西。

和 `PlayerBodyState` 正好反向——一个写位置，一个写意图。两个槽都是"玩家"这一层的东西，都不该经过业务世界。

### 意图怎么算

输入线程按当前按键合成方向向量，**先归一化再乘速度**（斜向走不会比直走快）：

```cpp
if (W) { dx += fwdX; dz += fwdZ; }
if (S) { dx -= fwdX; dz -= fwdZ; }
if (D) { dx += rgtX; dz += rgtZ; }
if (A) { dx -= rgtX; dz -= rgtZ; }
const double len = std::sqrt(dx * dx + dz * dz);
if (len > 1e-9) { dx /= len; dz /= len; }
controlOut_->vx.store(dx * kWalkSpeed_);
controlOut_->vz.store(dz * kWalkSpeed_);
```

`kWalkSpeed_ = 4.3`（MC 步行 4.317）。方向基向量与自由相机共用同一组，`yaw = 0` 时朝 -Z。

**没做加速/减速**：松手立即停。真要做惯性，得让物理侧维护一个当前速度并向目标速度插值，那是另一段的事。

### 跳跃

三件事必须按这个顺序：

1. 输入线程把空格取**按下边沿**（`spaceHeldPrev_`），只在玩家模式且按下瞬间置 `jumpRequested` —— 按住不会连跳
2. 物理线程 `exchange(false)` 消费
3. **在 `b.onGround = false` 之前判**，因为跳跃用的是上一个 tick 落地回退留下的结果，那行会把它抹掉

`kJumpSpeed_ = 4.9`，跳高 = v²/(2g) = 1.225 格，略高于 1 格台阶。

请求位先消费再判落地：空中按跳跃直接丢弃，**不做预输入**，不会落地瞬间自动弹起。

**空格在自由相机模式下仍是"按住上升"**，两种语义按模式分开，互不影响。

### 验收

| 时刻 | `生物1` | 说明 |
|---|---|---|
| sim=8.24s | (0, 4, 0) 在地面=1 | W 按下前 |
| sim=9.28s | (0.10, 4, -2.58) 在地面=1 | 走起来 |
| sim=10.32s | (0.28, 4, -7.05) 在地面=1 | 1.04s 走 4.47 格 → **4.30 格/s** |
| sim=11.36s | (0.43, 4, -10.66) 在地面=1 | W 松开前 |
| sim=12.40s | (0.43, **5.06**, -10.66) **在地面=0** | 跳跃，离地 1.06 格 |
| sim=13.44s | (0.43, **4**, -10.66) **在地面=1** | 落回同一水平面 |

`4.30 格/s` 与 `kWalkSpeed_ = 4.3` 精确吻合。跳跃完整走了一个抛物线：起跳 → 离地 → 落回。

x 有 0.43 格漂移（10.66 格位移里约 2.3°），是鼠标残留增量造成的，不影响方向判断。

截图：`build/ctrl2_walk_a.png`（走完，地平线约 50%）、`build/ctrl2_jump_b.png`（空中，地平线约 57%）。地平线整体下移，说明相机确实跟着玩家抬起来了。

### 顺带修掉的视角跳变

`ShowWindow(3)` 把窗口最大化后，光标相对窗口的坐标整体跳了一次，`cursorPosCb` 把这次跳变当成鼠标拖动，视角直接甩出去——玩家走的路线也跟着弯成 S 形。这就是之前截图里"满屏草地"的成因。

改法：回调里**先更新基准再判** `|dx|`、`|dy|`，超过 200 像素视为基准失效，只重设不转视角。正常拖动远小于这个量级，200 像素/帧已接近快速甩鼠标的极限。

对比证据（同一套按键脚本）：

| | 位置轨迹 | 每段速度 |
|---|---|---|
| 修之前 | `(0,4,0)` → `(0.65,4,0.24)` → `(-4.0,4,-6.3)` | 1.3 ~ 4.2 格/s 跳变 |
| 修之后 | `(0,4,0)` → `(0.43,4,-10.66)` 直线 | 稳定 4.30 格/s |

### 仍未覆盖

横向撞墙、顶头、z 轴回退。现在玩家能被推着走了，但这三条要**先在世界里造出障碍**才验得动——起点周边是平地，走过去撞不到任何东西。

## 十、玩家 API 的自由度分层（讨论记录，未定案）

本节是设计讨论的留档，**没有任何代码改动**，结论也未被采纳。

### 前提修正：模组动玩家，多数是"接缝"不是"改造"

把本地能查到的 30 个玩家 mixin（`sable-main` 20+、`ValkyrienSkies2` 10+、`Simulated` 4）按动机重排：

| 动机 | 代表 | 数量特征 |
|---|---|---|
| 玩家挡在我的系统前面 | Sable 的坐标搬家、VS2 的载具碰撞 | 少数但工作量最大 |
| 玩家需要操作我的东西 | `hold_interaction`、`quiet_use`、交互距离 | 多 |
| 想往玩家身上放数据 | `Simulated` 的 `PlayerMixin` | 多 |
| 想改玩家的数值 | 属性修饰符 | 极多 |
| 想重写玩家本身 | 无 | 几乎为零 |

**没有成熟模组去替换玩家的移动逻辑。** Sable 改玩家是因为它的坐标系和玩家位置对不上；Create 生态改玩家是因为玩家要操作机器、要被传送带运走。诉求是接缝，不是改造。

所以 API 的重点是**把玩家与各种系统的相交面都开出来**，而不是给模组重写玩家的权利。NeoForge 的 32 个玩家 event 文件分布吻合——交互、物品、会话、睡觉占满，移动物理一栏几乎为空。

### 自由度分六层，不能一档

| 层 | 自由度 | 给法 | 理由 |
|---|---|---|---|
| 数值（速度/跳力/重力/尺寸/视野） | 高 | 底座值 + 可叠加修饰符 | 冲突可用修饰符化解，不需要独占 |
| 状态与能力（飞行/游泳/攀爬/冻结/载具） | 高 | 可缺席的查询式能力 | 缺席不破坏"玩家存在"这个前提 |
| 数据（模组自己的进度、记录） | 高 | 每 body 一块旁挂内存 | 引擎不碰内容 |
| 行为 hook（每 tick 介入点） | 中 | 分段、限类型 | 全接管等于玩家不再由引擎管 |
| **位置权威** | **零** | 只由物理线程算 | 两个坐标系同时算 = Sable 那一整类 hack |
| **玩家存在性** | **零** | 引擎创建、引擎销毁 | 没玩家就没游戏 |

位置权威这条不是保守决定，是 Sable 用 20 多个 mixin 换来的教训：它保留原版 `Entity.move()` 算玩家位置，同时船有另一套坐标，于是碰撞要搬（`entity_sublevel_collision`）、上报要搬（`entities_stick_sublevels`）、视角要搬（`entity_rotations_and_riding`）、传送和重生要搬、冻结要搬——全是同一条根因的不同表现。

我们把位置锁在 `PhysicsWorld::moveKinematicAxis` 一处，等于一次性省掉了那一整类补丁。

### 三个具体设计点

**扩展字段用裸指针，不用字典**

```cpp
struct BodyDesc {
    // 形状：注册时定死，不可叠加
    double halfExtentX, halfExtentY, halfExtentZ;
    double centerOffsetX, centerOffsetY, centerOffsetZ;
    MotionType motion;

    // 数值：底座值，实际值由修饰符栈算出
    double walkSpeedBase;
    double jumpSpeedBase;

    // 模组扩展：引擎不读、不写、不释放
    void* ext;
};
```

不用 `unordered_map<string, variant>`：每次访问一次哈希，25 TPS × 生物数量 × 每 tick 查几次是纯浪费，且类型不安全。

不用 ECS（Entity Component System，实体组件系统）：它的收益在批量遍历同类型实体，玩家只有一个，收益为零，成本是每个系统都要重写。

`ext` 的语义要写进 API 契约：引擎完全不管这块内存，模组在 `onUnload` 里自己清。

**行为 hook 分段且限类型，不给整方法**

```
输入合成 → [hook: 改目标速度] → 物理积分 → 碰撞结算 → [hook: 落地后] → 状态写回
```

每个 hook 能改的数据类型声明死，不能改流程。对照 NeoForge 的 `PlayerEvent$BreakSpeed`：能改 `speed` 字段，改不了"怎么挖"。

**hook 必须状态触发，不是每 tick 无条件调**。飞行模组只在飞行时介入，Create 只在玩家操作机器时介入。所以能力查询每 tick 一次（一次虚函数调用），能力逻辑只在有这个能力时执行。装 10 个模组的成本差异因此是 10 次空查询 vs 10 次完整逻辑，差两个数量级。

**同类能力冲突走加载期拒绝**

两个模组都注册飞行能力：运行期先到先得会让后注册的静默失效，模组作者和玩家都不知道；加载期拒绝则直接报错不加载第二个。

按"让模组作者自由、不为其兜底"的立场选后者——两个模组都想接管飞行是模组作者之间的矛盾，引擎没有立场仲裁。

这条规则要在 `entity_api.h` 的能力注册函数签名里体现（注册得能返回失败）。

### 时间预算：不给

25 TPS = 每 tick 40ms，模组在 hook 里做重活会直接拖慢所有生物的物理。两种立场：给时间预算（超时跳过、记日志）会让模组"间歇性失效"，极难调；不给预算则一个烂模组毁掉整个物理线程。

倾向**不给**，与"不为模组兜底"一致，但要在 API 契约里写死：hook 不许阻塞、不许 O(n²)，40ms 预算是硬上限。

### 现在该做到哪一步

自由度不该一次全给。现在连"实体"这个概念都还没有（`bodies_` 只有数据没有行为），全套定死会在第二个生物进来时发现形状全错。

1. **先立 `BodyDesc`**：形状 + 数值底座，`ext` 留着但暂无人用
2. **再做属性 + 修饰符栈**：先纯引擎内部，`SpeedModifier` 只是 `{来源, 加减乘, 值}`，DLL 不参与
3. **能力查询只定形状**：一个空实现的 `hasCapability(id)`，先确认每 tick 查一次的位置
4. **hook 先只留一个点**（如"落地后"）：验证"模组代码在物理线程被调用"这条链路，以及它卡住时会发生什么

3、4 只定形状不实现，等有第二个生物再验。

### 未决分叉

**玩家能否被多个模组同时"部分接管"**（如 A 管水平移动、B 管竖直飞行）：

- **A 可以**：自由度高，但要给 `vx/vz/vy` 分别定义所有者，实现复杂
- **B 不可以**：任一时刻只有一条驱动链，要么引擎内置、要么某一个能力，简单可预测

倾向 B——与"同类能力加载期拒绝"是同一套逻辑：既然同类不能共存，"各改一半"的场景本身就不该存在。按 B 走，`PlayerControlState` 形状不用动，只需在物理线程里加一句"当前驱动者是引擎还是某能力"。

**用户明确表示本轮不解决此分叉。**
