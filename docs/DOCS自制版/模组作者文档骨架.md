# 模组作者文档骨架

> 定位：面向模组作者与第三方整合包作者，是模组 SDK 文档的骨架。
> 玩家侧不读本文档——玩家只知道"这是一个游戏，开箱即玩"。
> 状态：骨架（2026-11-09），详细内容随 API 实现逐步补充。
> 上下游：发布决策见《发布与商业架构决策.md》；玩家向文案见《玩家向说明.md》。

---

## 一、架构总览（作者视角）

| 层 | 内容 | 由谁提供 | 收费 |
|---|---|---|---|
| **本体（EXE）** | 引擎 + 核心系统 | 项目方 | 收费 |
| **官方整合包** | 全部玩法内容（方块/生物/群系/系统），以 DLL 形式实现 | 项目方 | 免费，随本体分发 |
| **第三方整合包** | 社区内容 | 模组作者 | 由作者决定 |

**关键原则**：官方内容走和第三方**完全相同的 mod API**——官方能做，第三方也能做。这是架构自证。

---

## 二、一个内容包（DLL 单元）的构成

| 组成 | 说明 |
|---|---|
| DLL | 编译产物，一个内容包 = 一个加载单元 |
| mod.json | 元数据：id / name / version / entry / load_phase / depends / 兼容引擎版本 / 是否声明 unsafe |
| 资源 | 贴图、模型、音效等（打包方式待定） |
| 目录约定 | 普通模组放 `mods/`；加载器放 `mods/loaders/` |

**加载规则**：

- 依赖解析：Kahn 拓扑排序，被依赖者先加载
- 加载阶段：按 `load_phase` 分阶段确定性执行
- 崩溃隔离：目标为单个 mod 崩溃不影响其他 mod 与本体

**待实现**：注册表来源标记、erase、启动期冻结窗口的最终行为。

## 三、官方整合包的打包标准（作者可直接对照）

| 项 | 标准 | 理由 |
|---|---|---|
| DLL 数量 | **1–3 个**（不做几十个散 DLL） | 加载速度、崩溃面、版本同步 |
| 内容 | 方块/生物/群系/系统全部走 mod API | 架构自证 |
| 版本 | 与引擎版本绑定发布 | 避免版本错配 |
| 资源 | 内置到 EXE 资源层 / 加密资产包（待定） | 防随意拆改 |

---

## 四、API 纪律

| 约束 | 内容 |
|---|---|
| 版本 | 全局 `kEngineApiVersion` + **追加纪律**：只追加，不破坏已有 API |
| 冻结窗口 | 启动期注册表冻结（硬约束） |
| 公开 / 特权 | 正当需求进公开 API；绕过规则/内部结构的能力进特权 API，声明 unsafe 才给 |
| SDK 范围 | 模组 SDK 只含 `modapi/`；引擎源码可见不等于布局稳定 |
| 版本声明 | mod.json 声明兼容引擎版本；启动器负责提示与兼容层 |

---

## 五、启动器（作者看到的接口）

| 功能 | 作者视角 |
|---|---|
| 版本管理 | 我的 mod 对应哪个引擎版本、哪个整合包版本 |
| 依赖解析 | 我声明的 depends 会被正确排序加载 |
| 崩溃提示 | 我的 mod 崩了，日志定位到哪里 |
| 整合包切换 | 玩家在官方包 / 第三方包之间切换 |

---

## 六、做一个 mod 的最短路径（工作流骨架）

1. 拿 SDK（`modapi/` + 示例工程）
2. 写 `mod.json`（声明 id、版本、依赖、加载阶段）
3. 编译 DLL
4. 放入 `mods/`
5. 启动器加载
6. 看日志调试

> 详细步骤待 SDK 成形后补充。

---

## 七、作者向验收标准

| 项 | 标准 |
|---|---|
| 最小可运行 | 一个空 mod 能加载、能注册、能卸载 |
| 依赖排序 | 两个有依赖关系的 mod 加载顺序正确 |
| 崩溃隔离 | 一个 mod 崩溃，本体与其余 mod 不受影响 |
| 共存 | 官方整合包与第三方 mod 可同时加载 |
| 版本兼容 | 引擎版本不匹配时，启动器给出明确提示 |
