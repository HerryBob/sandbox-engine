# 架构决策：注册表机制（模组地基）

>2026-10-26 定稿 · 2026-10-27 已实现验证（见第十一节）

## 一、动机

1. 引擎将走 **DLL 模组**路线：模组加方块/实体 = 调引擎注册 API，引擎不硬编码内容。
2. 借鉴 MC 教训：**数据格式早设计**（MC 1.13 扁平化把方块数字 ID 改命名空间字符串，迁移代价巨大；我们应提前做对）。
3. 模组基础的第一块砖 = **注册表机制**（没有它，DLL 模组"往哪注册"无从谈起）。

## 二、架构边界（与模组的分层）

```
┌─ DLL 模组层：调引擎 API，往注册表【塞内容】─────────┐
│   玻璃/铁矿/齿轮方块 → registerBlock(引擎API)        │
│   生物/实体类型      → registerEntity(引擎API)       │
│   模组私有表（配方/任务）→ 用引擎通用机制自建          │
└────────────────────────────────────────────────────┘
                    ↓ 依赖方向：模组依赖引擎，引擎永不依赖模组
┌─ 引擎核心层：内置注册表【实例】（引擎逻辑直接依赖）────┐
│   BlockRegistry ← 面剔除/网格生成/物理/存档都要查它   │
│   EntityRegistry（未来）                            │
└────────────────────────────────────────────────────┘
                    ↓ 依赖
┌─ 引擎机制层：通用注册表框架──────────────────────────┐
│   Registry<T>（模板：注册/查询/冻结/ID管理）           │
└────────────────────────────────────────────────────┘
```

- **机制进引擎**：Registry<T> 模板、注册/查询 API、冻结、ID 管理。
- **实例进引擎**：引擎核心逻辑依赖的注册表（BlockRegistry）由引擎内置。
- **内容归模组**：具体方块/实体逻辑由 DLL 注册；引擎启动注册 4 种基础方块作为"原版内容"验证机制。
- **模组私有表**：引擎核心不需要的注册表（配方等），DLL 用通用机制自建。

## 三、侵入式修改红线

```
物理上：C++ 同进程无隔离，DLL 可 inline hook/改导出表/vtable 覆盖（防不住）。
架构上：拒绝非受控侵入。
  受控侵入（允许）= 引擎开的窗口：注册表/事件/委托/回调。
  非受控侵入（禁止）= 绕过契约改引擎行为：hook、改码、覆盖核心函数。
原因：引擎内部必须"可推理"（掌控力）；MC Mixin 侵入式换来每版本全生态崩溃。
约束方式：规范契约（同 Linux 内核哲学），模组文档明令禁止 hook 引擎。
```

## 四、MC 注册表架构（参考蓝本，1.19.3 重构后）

```
① 双 ID 体系
   字符串 ID（ResourceLocation，如 minecraft:stone）
     → 人可读、存档/磁盘用、跨版本稳定
   数字 ID（raw ID，自动分配）
     → 网络传输/压缩存储用、跨版本不稳定
② Registry<T> 接口 + Registries（静态持有全部实例：BLOCK/ITEM/ENTITY_TYPE/…）
③ 冻结 freeze：静态注册表初始化后只读（渲染/物理免锁查询）；
   冻结后注册崩溃（"Registry is already frozen"）；模组在冻结前注册
④ 数据驱动：大量内容从 datapack JSON 加载（方块状态/模型/附魔/交易/世界生成）
⑤ Holder：注册对象包装，支持数据驱动引用替换
⑥ Codec：序列化（byNameCodec=字符串 / 压缩=数字）
```

## 四·补、万物皆注册表（多域扩展原则）

```
MC 哲学：Everything is a registry（几十个注册表：BLOCK/ITEM/ENTITY_TYPE/BIOME/…）
我们的原则：
  机制写一次（Registry<T>），每个域 = 实例化 + 语义薄封装（自定义方法）
    BlockRegistry  → 注册方块、查"是否不透明"（面剔除）
    EntityRegistry → 注册实体、查碰撞属性（未来）
    ItemRegistry   → 注册物品、查堆叠上限（未来）
  判断标准（两问即达）：
    ① 模组需要加这种新东西吗？  ② 引擎核心逻辑依赖查询吗？
    → 命中即注册表化；系统未出现时不提前建空表（不过度设计）
```

## 六、设计草案（明日实现）

```cpp
// 方块属性：模组加方块 = 注册一条 BlockInfo
struct BlockInfo {
    std::string_view name;   // "stone"（稳定名字，存档用）
    bool         opaque;     // 是否不透明（面剔除消费）
    float        hardness;   // 硬度（未来）
    // 未来：textureId / lightEmission / sound ...
};

// 注册表机制：注册 / 查询 / 冻结
template <typename T>
class Registry {
    std::vector<T> byId_;                            // 数字 ID → 对象（连续数组）
    std::unordered_map<std::string, std::uint16_t> byName_; // 名称 → 数字 ID
    bool frozen_ = false;
public:
    std::uint16_t add(std::string name, T value);     // 返回数字 ID；冻结后调用报错
    const T& get(std::uint16_t id) const;             // 数字查（O(1)，渲染主通道）
    const T* find(std::string_view name) const;       // 名称查（存档/调试）
    void freeze();                                    // 冻结：之后只读
};

// 引擎启动流程：
//   BlockRegistry 注册 4 种基础方块（stone/wood/dirt/air）
//   → 未来：DLL 在冻结前注册自己的方块
//   → freeze() → 渲染/物理线程免锁读取
```

## 十、渲染耦合与契约化解耦（2026-10-26 补充）

### 注册表必须进引擎的三条硬理由

```
① 查询基础：面剔除查 opaque、物理查碰撞、存档查名称
   —— 查询在引擎核心逻辑里，查询目标必须在引擎内
② 启动时序：渲染管线初始化就要读方块属性
   —— DLL 模组那时还没加载，引擎必须自带可用表
③ 线程安全：渲染线程免锁读（冻结表）
   —— 冻结机制是引擎的，表也必须引擎管
进引擎 = 机制 + 实例 + 基础条目；不进 = 方块具体内容（模组提供）
```

### 渲染器本体不能 DLL，渲染表现可以

```
渲染器本体（交换链/管线/绘制循环）= 引擎核心
  引擎启动就要跑（模组加载前），是引擎的生命线
  （Sodium 也没接管渲染器，它优化 vanilla 渲染的实现层）
方块的渲染表现（模型/纹理/渲染类型）= 模组注册时提供
```

### 深度耦合的解法：契约化（MC 同款）

```
耦合本质：渲染层需要方块的"渲染语义"
解耦关键：把语义抽象成契约，引擎只认契约

MC：
  引擎认 RenderType（solid/transparent/cutout）+ 模型引用
  （模型=数据包 JSON，渲染类型=引擎契约）
  → Sodium 能优化 vanilla：管线基于契约，优化的是实现

我们：
  BlockInfo 加 renderType 字段（契约）
  引擎面剔除/渲染按 renderType 走（不认方块是谁）
  方块外观（模型/纹理）：模组注册时提供（未来）
```

### 完全解耦不可行（认知底线）

```
彻底解耦 = 引擎不认识任何方块 = 通用网格桶
  → 面剔除/网格合并/实例化全没了 → 渲染性能退回逐方块绘制
渲染优化建立在对方块的理解上（物理现实）
MC 答案：不是完全解耦，是契约解耦
  引擎理解契约（solid/transparent + 模型引用），模组提供内容

## 十一、注册表归属判据：强绑定（2026-10-27 定稿）

### 强绑定 = 内置的判据（三问的本质）

> 用户提炼："是否内置主要看哪些东西的出现是强绑定的"。三问（核心逻辑查吗/启动时序要吗/线程免锁读吗）本质是强绑定的检查清单。

```
强绑定（tight coupling）三维度：
  ① 数据流绑定：渲染/物理/存档直接读它的数据
  ② 时序绑定：核心初始化顺序上离不开（模组加载前就要）
  ③ 行为绑定：核心机制的行为由它决定（面剔除 = f(opaque)）

判断一句："这个系统上线时，引擎核心代码会不会直接依赖它的数据？"
  会   → 内置（实现时间看系统排期）
  不会 → 外置（查询通道）
```

### 内置 / 外置 / 后置总清单

```
内置（强绑定，引擎建表 + 基础条目）：
  BlockRegistry            现在（三向强绑：面剔除/物理/存档）
  EntityRegistry           实体系统开工时（物理/AI/渲染/存档）
  BlockEntityTypeRegistry  有状态方块开工时（存档格式/渲染状态/物理传动）
  ItemRegistry             物品系统开工时（存档/渲染/背包）
  PhysicsInfo（物理参数表） 物理特性开工时（物理线程免锁读 —— 本项目独有强绑源）
  机制类（合成/掉落/AI/生成/UI 机制）—— 引擎执行它们，机制必须内置

外置（弱绑定，查询通道 / DLL / 数据）：
  具体配方 / 掉落表 / 生物群系参数 / 结构内容 / AI 行为 / 对话任务
  / UI 布局 / 方块外观 / 音效 / 按键绑定 / 数值平衡

MC 印证：
  RecipeType（配方类型=机制）内置 vs Recipe（具体配方）数据驱动
  Enchantment / DamageType 1.19.3 迁数据驱动
  —— MC 持续把"能弱绑定的"迁出核心，只留强绑定
```

### PhysicsInfo 拆分决策（用户拍板，2026-10-27）

```
物理参数【不合并】进 BlockInfo，拆分独立 PhysicsInfo 表：
  BlockInfo（渲染/存档域，必填）：name / opaque / hardness / renderType
  PhysicsInfo（物理域，可选）：pushable / mass / friction / strength

理由：
  ① 职责独立：渲染逻辑查渲染表，物理逻辑查物理表，互不污染
  ② 模组友好：普通方块只 add BlockInfo；特殊物理方块（冰/箱子/移动块）才 add PhysicsInfo
  ③ Registry find 的 nullptr = 天然"默认行为"
     （没注册物理条目 → 不可推/标准摩擦，零额外设计）
  ④ 两张表各自 freeze → 各自免锁读 → 线程隔离干净

（原"物理参数并入 BlockInfo"方案作废，理由：合并时模组每次 add 都要带结构，
 拆分时"没注册 = 默认"由 nullptr 表达，更强）
```

### 静态属性 vs 动态状态（BlockEntity 边界）

```
静态属性（所有同类型方块一样）→ BlockInfo / PhysicsInfo（类型表，一个类型一条）
动态状态（每个实例不同：齿轮转速 / 箱子库存）→ BlockEntity（实例数据）
  —— 实例数据是区块里 blocks[] 之外的第二通道（未来加）
  —— 把动态状态塞进类型表 = 一个齿轮转，所有齿轮都转（错）
```

### 模组如何碰内置表：注册窗口（RegistryAccess）

```
内置 ≠ 模组碰不到。引擎建表 + 注册阶段开"窗口"：

引擎启动时序：
  ① 建表（含基础条目）→ ② 加载 DLL，递 RegistryAccess 窗口
  ③ DLL 通过窗口 add 自己的条目 → ④ freeze → ⑤ 运行期只读

窗口形态（伪代码）：
  struct RegistryAccess {
      bool (*addBlock)(std::uint8_t type, const BlockInfo& info);
      bool (*addEntityType)(std::uint16_t id, const EntityTypeInfo& info);
  };
  extern "C" __declspec(dllexport) void Mod_Register(const RegistryAccess* access);

受控侵入精髓：
  模组只拿到窗口（addBlock/...），碰不到表内部（unordered_map/frozen_/锁）
  冻结后窗口也失效（add 返回 false）
  红线：只接受窗口内注册，拒绝非受控 hook（inline hook / vtable 覆盖）
  —— MC Mixin 侵入式换来每版本全生态崩溃，我们规范契约（同 Linux 内核哲学）
```

### Create（机械动力）对照

```
Create 注册方块（Forge）：AllBlocks 集中类 + DeferredRegister（延迟注册器）
  BLOCKS.register("cogwheel", CogwheelBlock::new, 属性...)
  → MOD_REGISTRATION 事件统一提交进 MC 的 Block 注册表

自制类体系：Block → KineticBlock（动能基类）→ CogwheelBlock/ShaftBlock/WaterWheelBlock
  方块实体：BlockEntity → KineticBlockEntity → CogwheelBlockEntity...

关键认知：模组注册的是【方块对象】进引擎内置表；表还是引擎的、条目是模组的
  —— 同款"注册窗口"机制（DeferredRegister = RegistryAccess 的对应物）

C++ DLL 注意：Java 的 Block 子类体系不能照抄
  —— 跨 DLL 类继承 + vtable 有 ABI 风险
  —— 原型建议"纯数据 + 行为回调"，抽象接口 IBlock 等模组 API 稳定后再上
```

### 编译期校验（引擎检查放引擎内部）

```
两类检查区分（判据：删掉它游戏还正确吗）：
  语义检查（必留，release 也在）：
    frozen 拒绝 add —— 免锁读契约，删掉会崩
    重复 add 拒绝（emplace().second 天然实现，零开销）
  校验层（debug 才有，release 编译消失）：
    assert（get 找不到 key、冻结后调 add 等程序 bug）
    if constexpr (ENGINE_REGISTRY_CHECKS) —— 编译期决定
    —— 比 Vulkan 校验层更彻底：release 构建校验代码整体不存在
```

### RenderType 渲染方式分类

```
enum class RenderType : std::uint8_t {
    Solid = 0,       // 实心：深度写+测
    Cutout = 1,      // 镂空（树叶/铁轨）：alpha 测试 + 写测
    Translucent = 2, // 半透明（玻璃/水）：混合 + 排序 + 不写深度
};

要点：
  半透明 ≠ 改个 flag —— 是渲染管线分桶（opaque pass / translucent pass）
  消费后置：分桶管线实现时启用；当前全 Solid 行为不变（字段先有，管线后做）
  正交：渲染方式 ≠ 物理碰撞
    （玻璃 translucent 但有碰撞；水 translucent 无碰撞 → 碰撞归 PhysicsInfo）
```
