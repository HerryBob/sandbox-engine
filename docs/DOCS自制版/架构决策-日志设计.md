# 架构决策：日志设计（现状记录 + 演进方向）

> 日期：2026-10-28 · 状态：待办决策（未实现）· 触发点：模组接入 / 日志量上升

## 1. 现状（三处耦合）

| 位置 | 现状 |
|---|---|
| `BusinessWorld::maybeLog()` | 业务类内拼字符串（ostringstream）+ 自己算 tps + 自己定节流（每秒一条） |
| `PhysicsWorld::maybeLog()` | 同款复制 |
| `main.cpp` 的 `std::cout` | 引擎入口裸输出 |

`core/Log.hpp` 提供 `engine::core::log(level, str)` —— 已有集中点，但**无级别过滤、无输出目标配置、无分类**。

## 2. 问题（理论层面）

1. **职责混**：调度/物理逻辑不该关心"日志一行长什么样"——maybeLog 混着统计读取 + 格式化 + 输出策略三种职责。
2. **输出策略硬编码**："每秒一条"写在业务类里；想改频率/级别过滤得动引擎代码。
3. **模组无法打日志**：dll 模组不能调用引擎内部函数——日志必须成为公开 API（与注册表同理）。

## 3. 演进目标（未来实现）

```
业务代码：log.info("放置方块 pos={}, type={}", x, y, z);  ← 只声明"发生了什么"
日志层（spdlog/glog 式抽象）：
    │ 级别过滤（trace/debug/info/warn/error）
    │ 多 sink（控制台 / 文件 / 异步队列）
    │ 格式策略（时间戳 / 线程名）
    └─ 全部集中在日志模块，业务代码零感知
```

- **公开 API**：模组可调（引擎对外 SDK 的一部分）。
- 拆分时不动业务逻辑：业务代码保持"语义化事件"，输出策略全部下沉日志层。

## 4. 触发信号（满足任一即动手）

| 信号 | 现状 | 临界 |
|---|---|---|
| 日志量 | 每秒几条，可忽略 | 每秒上千条（需异步、丢帧诊断） |
| 输出目标 | 单一 stderr | 需分文件 / 轮转 / 按级别归档 |
| 消费者 | 仅自己看控制台 | 模组作者要打日志 |
| 格式化成本 | 节流后近零 | 关键路径频繁打日志 |

## 5. 原则（记入）

- **业务代码说"发生了什么"，日志层决定"怎么输出"**。
- `core::log` 进化为带级别 + sink 的公开 API（spdlog 风格抽象，不引入第三方库亦可自实现）。
- 原型阶段维持现状（量小、人肉可读、集中点已有），不为此重构。
