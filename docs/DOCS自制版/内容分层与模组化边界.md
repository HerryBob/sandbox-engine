# 内容分层与模组化边界

> 定位：定义"引擎负责什么、模组负责什么"，是《模组作者文档骨架.md》的上游——这份定边界，那份写接口。
> 原则：**引擎给能力，模组给内容。**
> 状态：初版（2026-11-13），具体 API 形态待 SDK 定案。

---

## 一、总原则

> 引擎负责"世界能做什么"（能力）；模组负责"世界里有什么"（内容）。
> 判断一个东西属于哪一层，看**替换它会不会破坏别人**：会 → 引擎；不会 → 内容。

---

## 二、三层结构

### 第 1 层：引擎内核（不可替换，模组不能改）

| 模块 | 内容 |
|---|---|
| 世界存储 | 区块、方块 ID 空间、存档格式、坐标系 |
| 物理内核 | 刚体、碰撞检测、结构装配、约束求解 |
| 渲染管线 | 图集、网格构建、材质、Vulkan 后端、视锥/遮挡 |
| 加载器与 API | modapi 版本、Phase、注册表、DLL 生命周期 |
| 时间循环 | tick、每帧更新顺序、跨线程调度 |
| 网络同步 | 客户端/服务端、状态复制 |
| 输入与窗口 | 键鼠、窗口管理 |
| 资源与文件系统 | 资源索引、挂载路径、优先级 |

> 这一层的原则：**稳定优先于灵活**。改它需要引擎版本更新，会破坏所有模组。

### 第 2 层：引擎能力层（不可替换，但参数可调）

| 能力 | 说明 | 可调部分 |
|---|---|---|
| 结构运动约束 | 装配体、关节、质量/重心计算 | 上限值、精度、是否启用 |
| 连续传输 | 管道/传送带/滑槽的求解 | 流量上限、精度 |
| 批量处理 | 区块/实体的批量更新 | 批大小、调度策略 |
| 流式加载 | 区块加载、LOD | 距离、预算 |
| 动态渲染 | 移动结构的渲染 | 画质档位 |
| 风场 | 3D 矢量场求解（温差/地形/高度/湍流） | 强度、区域、频率（参数），求解在引擎 |

> 这一层是"全功能方块化"能成立的前提：**能力在引擎，玩法在方块**。

### 第 3 层：内容层（模组化，可替换可改造可扩展）

| 内容 | 例子 |
|---|---|
| 方块定义 | 6 类功能方块的具体实现、材质参数（质量/摩擦/强度） |
| 生物 | 模型、贴图、动画、AI 参数、音效 |
| 地形生成 | 噪声层配置、群系、特征、资源分布 |
| 物品与配方 | 物品、合成表、加工链 |
| 遗迹与结构 | 教学遗迹、自然奇观 |
| 天气与风参数 | 风强度、季节、区域特性 |
| UI/HUD | 界面、菜单、提示 |
| 音效音乐 | 环境音、交互音、BGM |
| 玩法规则 | 威胁强度、难度曲线、资源节奏 |
| **官方整合包** | 官方内容 = 一组模组（无特权） |

---

## 三、判断标准（三问）

任何新东西，过三问：

1. **所有模组都需要它才能跑吗？** → 是：引擎内核
2. **替换它会不会破坏其他模组？** → 会：引擎内核或能力层
3. **它只决定"世界里有什么/怎么表现"吗？** → 是：内容层

**边界案例**：

| 对象 | 归属 | 理由 |
|---|---|---|
| 风场求解 | 引擎能力 | 所有模组共享同一个风场 |
| 风的强度/区域 | 内容 | 一个模组可能想做"无风世界" |
| 结构物理 | 引擎能力 | 所有结构共享同一套求解 |
| 什么方块能造出结构 | 内容 | 由方块的材质/连接属性决定 |
| 基础寻路/感知 | 引擎能力（通用） | 所有生物共享 |
| 生物的行为树 | 内容 | 每只生物不同 |
| 方块 ID 空间 | 引擎内核 | 全局唯一，改了就冲突 |

## 四、模组化的三种粒度

| 粒度 | 含义 | 例子 |
|---|---|---|
| **可替换（Replace）** | 同 ID 覆盖原实现 | 换方块贴图、换生物模型、换 UI 主题 |
| **可改造（Modify）** | 保留 ID，改参数/行为 | 改方块质量与摩擦、改生物 AI 参数、改风强度 |
| **可扩展（Extend）** | 新增内容，不动原有 | 新方块、新生物、新群系、新配方 |

> **"可替换"是硬承诺，"可改造"是参数级承诺，"可扩展"是默认能力。** 三者用不同机制的模组实现，不能混。

---

## 五、硬约束：官方内容无特权

> 官方整合包必须和自己的模组走**同一条通道**（同一个 API、同一个注册流程、同一套打包规范）。

理由：
- 一旦官方内容走特权通道，边界就会腐烂——"官方能做的，模组不能做"
- 官方内容是最强的"可替换性证明"：玩家能替换官方内容，才知道真的可替换

---

## 六、技术前提（注册表）

> "可替换/可改造"在技术上依赖注册表的三个能力，缺一样都做不到：

| 能力 | 作用 | 现状 |
|---|---|---|
| **来源标记** | 知道每个注册项来自哪个模组（用于冲突排查与卸载） | 待补（已知缺口） |
| **覆盖优先级** | 后加载的模组可覆盖先加载的同 ID 项 | 待定 |
| **erase** | 卸载/替换时能安全移除注册项 | 待补（已知缺口） |

> 这三项不解决，"可替换"就只是口号。
