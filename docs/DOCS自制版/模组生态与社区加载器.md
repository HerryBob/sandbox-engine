# 模组生态与社区加载器

> 记录 2026-11-21 讨论结论。**目前不实施**，等人来写第一个外部模组再说。

## 一、结论

- **加模组不需要改 CMake**：`ModLoader::loadAll("mods")` 扫目录找 `*.dll + mod.json`，运行时全动态。玩家把目录丢进 `mods/` 即可。
- `CMakeLists.txt` 里的 4 处（`add_library` / `POST_BUILD` 拷贝 / `foreach` 资源 / `add_dependencies`）只是**仓库内自带模组的构建方式**，与"玩家加模组"是两条独立的路，随时可以去掉。
- **社区能写模组，但暂时写不了加载器** —— 加载逻辑（扫描/排序/拒绝/回滚/卸载）全在 `ModLoader.cpp`，没有接缝。

## 二、三个缺口

| # | 缺口 | 现状 | 阻碍什么 |
|---|---|---|---|
| ① | **清单缺元数据** | `mod.json` 只有 `id / phase / dependencies`；版本号只在 DLL 的 `vtbl->version()` 里 | 加载器无法在 `LoadLibrary` 之前做版本求解 |
| ② | **加载权在 exe 里** | 扫描、Kahn 排序、拒绝策略、卸载顺序全在 `ModLoader` | 社区 loader 只能写"离线依赖求解器"，不能替换加载流程 |
| ③ | **没有自省 API** | 模组只能 `getWorldInfo` | loader / HUD / 调试无法列出"加载了哪些模组、什么版本" |

## 三、四步路线（按代价从低到高）

| 步 | 做什么 | 改动量 | 何时做 |
|---|---|---|---|
| **1** | `mod.json` 加 `version` / `apiVersion` 范围 / `dependencies` 带版本 / `provides` / `conflicts` | `Manifest.cpp` ~60 行 | **第一个外部模组出现时** |
| **2** | 加 `getLoadedMods(host, out, capacity)` 只读 API（`{id, version, phase}`） | ~40 行 | 同 1 |
| **3** | 写《模组清单规范》文档 | 文档 | 同 1 |
| **4** | **加载器 DLL 化**：引擎先加载 `mods/loader.dll`，把排序/依赖委托给它 | 大 | **只在真有加载器作者出现时**考虑 |

**第 4 步为什么先不做**：它要求引擎把"排序、拒绝、级联、回滚、卸载"全部变成 loader 的责任，并为此暴露大量内部能力（注册表操作、卸载回调）—— 与"最小暴露面"冲突，且现在没有任何需求方。

## 四、为什么"清单扩展"是共同前置

同一个 `mod.json` 规范，对两边都必要：

- **模组作者**：声明自己需要什么、提供什么、与谁冲突
- **加载器作者**：在加载前做依赖求解与冲突检测

所以第 1 步无论走哪条路都得做，且**不需要引擎行为变化**（只加校验和字段）。

## 五、相关约束（已成立）

- 模组入口是纯 C（`CreateModC` + `ModVtbl`），任何能产出 native DLL 的语言都能写模组
- 跨 DLL 只传 POD + 函数指针，`modapi/` 下全部是 C 头
- 清单非法 / 依赖缺失 / 成环 → 拒绝加载并记日志（见 `bug记录.md` B2：跨批环依赖目前漏拒）
