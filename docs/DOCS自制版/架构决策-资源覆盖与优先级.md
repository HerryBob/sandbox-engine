# 架构决策 · 资源覆盖与优先级

> **状态**：设计结论已成型（2026-11-25），未动工。
> **取代**：`模组资源与数据处理.md` 第四节「冲突规则」（那里写的是"引擎先登记所以引擎优先"，本文把语义反过来）。
> **前置**：不改覆盖语义，下面所有项都不成立——`ResourceIndex` 现在是"先到先得"，方向与本文相反。
> **外部依赖**：世界级材质包真正生效，需先有"图集可重建"，见 `未来方向-图集改造.md` T1。

## 一、当前基线（2026-11-25 实测）

| 维度 | 现状 | 代码位置 |
|---|---|---|
| 索引形态 | 一个全局单例，assets / data 两张 `unordered_map` | `ResourceIndex.hpp:52-57` |
| 条目字段 | 只有 `path` + `owner`，无来源层、无优先级 | `ResourceIndex.hpp:20-23` |
| 冲突语义 | **先登记者赢**，后来者 `WARN` 后完全忽略（不是降级，是查不到） | `ResourceIndex.cpp:43-49` |
| 登记顺序 | 引擎先（`main.cpp:276-277`），再由 `ModLoader` 每加载成功一个模组追加 | `ModLoader.cpp:303-309` |
| 模组先后 | phase 升序 → `manifest.id` 字典序（隐式，作者不可见） | `ModLoader.cpp:144-152` |
| 模板注释 | 明写"先登记者优先" | `ResourceIndex.hpp:4`、`main.cpp:275` |

**实际优先级链**：`引擎 > builtin 模组 > 用户模组（按 phase、id 字典序）`。

这条链有两个隐患：

1. **引擎排第一是"碰巧安全"**。引擎 `assets/` 现在只剩 `default.png`（缺失兜底）与 `font/ascii.png`，它们恰好应该不可覆盖；但规则没写进代码，等引擎再放一张内容贴图，它也会被锁死。
2. **"玩家包永远排最后"**，覆盖能力等于不存在。玩家 / 世界级的包必然是最后登记的，永远输给所有模组。

## 二、结论：一条规则，两条链

不建跨类型的统一优先级。**data 由 Server 管辖，assets 由 Client 管辖，两者不共用优先级空间**；于是"服务器管数据、客户端管画面"不需要额外仲裁规则。

同一条层序规则应用两次：

```
data 链（Server 管辖）            assets 链（Client 管辖）
L0 模组                           L0 模组
L1 全局数据包  data/               L1 全局材质目录  assets/
L2 世界数据包  <save>/datapacks/    L2 世界材质    <save>/packs/
```

**方向**：`L0 → L1 → L2`，后者覆盖前者。文档里一律用这个写法，不用 `>` 号，避免被读成"L0 最大"。

**没有"引擎内置内容层"**。`assets/` 与 `data/` 就是安装目录下的全局包目录（等价于 MC 的 `resourcepacks/` 与全局 `datapacks/`），不是引擎私有资源。模组是最底层，其余全是"安装者/玩家放进来的包"。

**内置兜底不参与层序**。`flat` 噪声定义（`NoiseDefTable.cpp:44-48`）与默认预设（`PresetLoader.cpp:58-68`）是代码里的兜底，只在"表里查不到对应名字"时生效，不是某一层的条目。

## 三、谁提供哪一层

| 层 | data（Server 管辖） | assets（Client 管辖） |
|---|---|---|
| L2 世界 | `<save>/datapacks/`，服务端权威 | `<save>/packs/`，客户端自己放 |
| L1 全局 | `data/`（安装目录） | `assets/`（安装目录） |
| L0 模组 | `mods/<id>/data/`，两端必须一致 | `mods/<id>/assets/`，两端必须一致 |

三条推论：

- **assets 链完全是客户端的**，服务端不提供任何材质，也不推包。因此不存在"客户端拒绝服务端材质"这套机制——没有可拒绝的东西。
- **data 链完全在服务端**（单机时服务端就是本地进程内的集成服务端），客户端一层都不提供。
- 联机时客户端**不持有世界数据**（区块流式接收、不落盘）；世界级 data 只认服务端那份，客户端本地同名包不参与。

**归属落在 Server 而不是 World**：Server 持有 data 的层栈，World 只是 Server 内的一个世界，L2 的包按世界分。这样与"assets 归 Client"对称；将来一个 Server 带多个 World 时，只需按世界键切换 L2。

### 联机形态（2026-11-25 定）

**走 MC 的道路：先实现集成服务端（integrated server），专用服务器（dedicated server）远期。** MC 的两种形态是：

- **集成服务端**：同一进程内同时跑 Server 与 Client 两套逻辑，Server / Client 是**逻辑对象边界**，不是进程边界。单机游戏就是这个；"开放局域网"只是把集成服务端绑到端口。
- **专用服务器**：独立 headless 进程，无窗口、不渲染，客户端走网络连过去。

三条落点：

1. **层栈归属跟着对象走**：data 层栈由 Server 对象持有，assets 层栈由 Client 对象持有，两者在同一进程里共存。单机下 `kind` 参数分派到两份表（`ResourceIndex.hpp:14-17`），不需要拆进程。（当前尚未建独立的 Server 对象，归属先按语义记录，等集成服务端真正落地时再挂上去；不要为此提前新建空壳类。）
2. **`side` 不做加载门禁**：集成服务端下客户端一直在跑，`client` 模组必须加载，门禁没有可触发场景。字段只做声明一致性校验与联机校验清单。
3. **从现在起生效的纪律**：Server 侧代码**不得直接依赖渲染**（Vulkan / GLFW / 窗口），需要表现层变化（方块变更、实体生成）时走事件或接口，由 Client 侧订阅。这是将来能拆出 headless 服务端的前提——MC 的 `server.jar` 里没有渲染代码，靠的就是这条边界。现在不守，将来拆分要扒一层皮。

#### 角色 × 加载面（2026-11-25 补充）

| 角色 | data 层栈 | assets 层栈 |
|---|---|---|
| 单机（一个进程，两个角色） | 模组 → 全局 `data/` → 存档 | 模组 → 全局 `assets/` → 存档 |
| 联机 · 房主（集成服务端 + 客户端） | 模组 → 全局 `data/` → 存档 | 模组 → 全局 `assets/` → 存档 |
| 联机 · 客人（纯客户端） | **不存在**（全部来自房主下发） | 模组 → 全局 `assets/`（**无存档层**） |
| 专用服务器（headless） | 模组 → 全局 `data/` → 存档（按世界分） | 不加载 |
| 专用服务器 · 客户端 | 不存在 | 模组 → 全局 `assets/`（无存档层） |

三个结论：

- **客人进程里没有"服务端"角色**，不是"有服务端但不加载"。所以 data 层栈的构建入口必须挂在"服务端角色启动"，而不是"进程启动"——否则客人会误建一份，读到本地不该生效的包。
- **"不相干"只适用于 assets**：房主与客人的画面各按自己的包渲染；但**模组必须两端一致**（否则进不去），**data 完全从属房主**。
- **客人客户端没有存档层**：他没有本地世界，本地的 `saves/` 与安装目录 `data/` 在联机时一律不参与。

一个可接受的副作用：房主若在存档里放了材质包，他自己看到的画面与客人看到的会不同。MC 的默认行为就是这样，不需要补齐。

## 四、覆盖语义（硬前置）

**① 后者覆盖。** 把 `ResourceIndex.cpp:43-49` 的 `emplace` 改为"比较后覆盖"，并记录覆盖链。这是所有后续项的地基。

**② 层内排序：`priority` 降序 → 名字升序。** `priority` 放 `pack.json`，缺省 0；同值时按目录名升序，保证每次启动结果一致。

**③ 层号是硬边界。** `priority` 只在层内比较，**不能靠一个大数字跨层越级**。否则一个模组写 `priority=999` 就能压过世界包，链失去意义。

**④ 不做受保护集合（2026-11-25 定）**。`textures/block/default.png` 与 `textures/font/ascii.png` 按普通资源走正常层序，可被上层覆盖或缺失；缺失时按现有兜底逻辑处理。后续 HUD 模组化会把字体图移走，这条不再需要特殊规则。

**⑤ 覆盖链日志。** 启动即打印，这是"可预测"的可验证形式：

```
[资源] 冲突 3 项
  textures/block/stone.png
    采用 L2 <save>/packs/hd (priority 10)
    落败 L0 builtin_blocks (priority 0)
```

**⑥ 条目字段要扩。** `ResourceEntry` 需要加 `layer` / `priority` / `order` 三个字段；`owner` 保留（已用于失败日志与跨模组引用告警）。`path` 的 `fs::path` **不提前抽象成"路径或远端标识"**——后续架构重构会大改这块，现在不预支设计。

**⑦ 登记时机要改。** 现在是引擎目录先登记（`main.cpp:276-277`）、模组后登记，正好把链做反。改成：先跑完全部模组加载并登记它们的资源 → 再登记全局 `assets/`、`data/` → 进入世界时再叠 L2。顺序即优先级，低到高。

## 五、命名空间

要覆盖原版，就必须知道"原版叫什么"。本引擎的内容在 `builtin_blocks` 模组里（`BuiltinBlocksMod.cpp:43-131`），路径没有命名空间，索引键是 `textures/block/stone.png`。

**默认命名空间定为 `mygame`**（游戏名未定，不占用 `minecraft`）：

- 内置模组产出的资源归 `mygame:`
- 玩家想覆盖原版，写 `assets/mygame/textures/block/stone.png`
- 将来改名只需改一处常量

连带改动：`def.texture = "stone"` 这类裸名要变成带 ns 的标识，`g_blockRegistry` 的按名查找跟着变。这是**破坏性改动**，不是顺手加。

## 六、模组单端 / 双端（**保留**）

MC 的 `environment: "client" | "server" | "*"` 描述的是**物理端**（physical side，哪个进程），它唯一的真实行为是"专用服务器加载时跳过 client 模组"。本引擎当前形态是集成服务端（单机 / 局域网，同一进程内跑两套逻辑），所以这个字段**不能当加载门禁用**——那会是永远为真的假条件。

保留它，但只保留**声明层**，三个行为按价值排序：

| 行为 | 说明 | 现在做 |
|---|---|---|
| 声明一致性校验 | `side: client` 却注册了方块 / 实体类型 → 拒绝加载并报错；`side: server` 却声明 assets 目录 → 警告 | ✅ |
| 联机校验清单只收 `both` / `server` | 纯客户端模组不参与版本比对，玩家装美化模组不被踢 | ✅ |
| 资源登记按 side 过滤 | 收益小，可改为看目录里有没有对应子目录 | 可选 |

**不做**：headless 加载门禁。形态已定为集成服务端（见三·联机形态），没有"无渲染进程"，门禁没有可触发场景。等专用服务器（独立 headless 进程）真落地再加，那时字段才获得第二个行为。

**字段设计注意**：`side` 只管"在哪加载"，**不承担"是否参与同步校验"**。两者是正交问题（纯 UI 美化 = 双端装但不需严格一致；服务端权威逻辑 = 单端但必须校验）。现在只留一个字段，但别把语义塞满，将来加第二个字段时不用改定义。

**同步范围**：参加强制同步的是**模组清单 + 版本 + 内容哈希**（代码和它自带的 assets / data），**不含玩家 `packs/` 与 `data/` 目录里的包**。否则只想换画面的人会被挡在门外。

## 七、执行顺序

| 序 | 动作 | 验收 |
|---|---|---|
| 1 | `ResourceIndex` 覆盖语义：先到先得 → 后者覆盖 + 覆盖链日志 | 同一文件被引用两次，日志能打出胜负双方；`find` 返回高优先级那份 |
| 2 | 登记顺序反过来：模组先、全局 `assets/`+`data/` 后 | 模组放的 `stone.png` 会被全局 `assets/` 同名文件覆盖 |
| 3 | 建立 `data/` 全局数据包目录（当前不存在） | 空目录静默跳过（`ResourceIndex.cpp:23`）；放入一个包后能覆盖模组同名条目 |
| 4 | 命名空间（默认 `mygame`） | 在 `assets/mygame/textures/block/` 放同名图能覆盖内置方块贴图 |
| 5 | 两条层栈：保留 `kind` 参数分派，内部两份带层栈的表 | 外部 15 处调用点无需改签名；`g_resourceIndex` 仍是门面 |
| 6 | `side` 字段 + 声明一致性校验 | 把 blocks 模组标成 `server`，其 assets 目录告警；标成 `client` 则拒绝注册方块 |
| 7 | 世界层载体 `<save>/datapacks/` 与 `<save>/packs/`（依赖存档机制） | 进世界叠加、退世界回滚，图集与 mesh 重建 |

第 7 项的真正门槛是**图集可重建**：`VulkanContext.cpp:1053` 现在只构建一次、`:1057-1059` 上传一次，不改这条，世界级材质包永远不生效。连带 `entityTextures_`（`:1226`）与 chunk mesh 重建（81 chunk ≈ 270 ms）。

## 八、明确不做

- 不建跨类型的统一优先级数字（data 与 assets 各自独立）
- 不做受保护集合（`default.png` / `ascii.png` 按普通资源走）
- 不做服务端推送材质包，也不做客户端拒绝机制（服务端不负责材质）
- 不做"用户可拖拽顺序"UI（第一版只给每包启用 / 禁用）
- 不做 headless 加载门禁（等专用服务器）
- 不把 `side` 拆成两个字段
- 不提前把 `ResourceEntry.path` 抽象成远端标识（后续重构统一处理）
- 不做逐 sprite 缩放（见 `未来方向-图集改造.md`）
