# 流体与气体系统：评审意见与切片计划

日期：2026-11-26　│　对象：`流体与气体系统设计.md`（v2 三态离散）
性质：**讨论记录，未到实现阶段**。本文不改原文，只记录评审结论、市面对照与验证计划。

---

## 0. 总体判断

范式（三态 + 规则海 + 活跃集 + 找平）本身是**被验证过的组合**，不是拍脑袋；
真正贵的部分不在流体算法，而在**边界定义**与**集成触点**。

```
算法核心（三态/规则海/找平）      → 对 ✅
边界定义（同列多水体/瀑布/卸载）   → 缺，必须先定
集成触点（物理力/网格调度/方块变更/存档）→ 缺，实现前需补
数值细节（收敛/守恒/精度）        → 有具体可改法
```

## 1. 结构性问题（会限制玩法边界）

### 1.1 为什么"一列只能有一个水面"（以及想突破有哪几条路）

#### 根本原因：存的是"量"，"位置"是推出来的

```cpp
struct WaterCell { float depth; bool isSource; };   // 只有一个数
```

结构里**没有存"水的底部在哪"**，`z_b` 是推导出来的：

```
z_b = 这一列最低的固体方块之上
```

即隐含假设：**水永远只占据这一列"最下面那一段空气"**。

这个假设在 **heightmap 世界**永远成立（一列只有一个空气区，无悬空、无洞穴）——
城市天际线、水力侵蚀那类地形游戏因此天然正确。
**体素世界会失效**：

```
    y=62  ┌──────┐
          │ 空气 │  ← 地表湖水面（第 1 个空气区）
    y=60  ├──────┤
          │ 岩层 │
    y=24  ├──────┤
          │ 空气 │  ← 洞穴湖水面（第 2 个空气区）
    y=20  └──────┘
```

两个空气区，但结构只有一个 `depth`；`z_b` 该取 20 还是 60——**推导本身二义**。

#### 硬保留一个 depth 会发生什么

| 失败 | 表现 |
|---|---|
| 质量消失/错位 | 洞穴的水被算到地表段或反之；灌满一个坑，另一个坑的水"没了" |
| 画不出来 | 渲染是"每列一个水面 quad"，一个 quad 只能一个高度 → 第二个水面无处安放 |
| 查询二义 | 浮力问"该 body 的水面高度"，同一列两个答案 |

#### 三条升级路（按实施成本排序）

| 方案 | 数据结构 | 成本 | 适用 |
|---|---|---|---|
| **A 存 bottomY + depth** | 每列仍 1 段（+1 字节） | 极低 | 只解决"水在台地而非最低处" |
| **B 按连通水体分高度场** ⭐ | 每个水体各自一份列→depth 表；列存 1~N 个水体 id | 中 | 通用；**与现有"三态+找平"最契合** |
| **C 逐体素水位（MC 路线）** | 每格一个水位 | 中高（复杂度） | 想要完全自由的水 |

#### 关于 C：内存不是拒绝它的理由

```
12 chunks 区域 = 3072 列 × 16 格高 = 49,152 格
4 bit/格（0..8 水位）≈ 24KB
1 byte/格            ≈ 49KB
```

真实成本不在内存，而在：
1. "静水零算"变伪命题（20 格深的海洋有 20 倍格子都要存/查）
2. 渲染从"一列一个平滑 quad"退化为逐面
3. 找平从"列间转移"变成"格间 6 邻域转移"

#### 为什么 B（按连通水体分高度场）最值得作为升级首选

**不连通的水体本来就不相互作用**——上面的湖不会流到下面的洞穴湖。所以：

```
水体 A（地表湖）：自己的一列 depth 表
水体 B（洞穴湖）：自己的一列 depth 表
列 → 只属于它所在的那 1~N 个水体
```

| 优点 | 说明 |
|---|---|
| 找平逻辑**完全不用改** | 每个水体内部仍是"一列一个 depth" |
| 内存只在重叠列处增加 | 洞穴湖通常很小；大海是规则水，零数据 |
| 与活跃集天然对齐 | 鼓动的是"某个水体"，其余水体完全不动 |
| 顺带解决气室 | 舱内水体就是"另一个水体" |

**代价**：维护"列 → 水体列表"索引；水体分裂/合并（挖穿隔层时两个水体合并）。

#### 结论

```
1.0：限制为"每列一个水面" —— 不是做不到，是**范围控制**。
     文档写明：一列只保留最低连通水面，其余空腔干燥（合并规则见 §3 决策 1）。
将来实现流体时，按 A（bottomY）→ B（分水体）→ C（逐体素）的顺序逐个尝试，
     先做最小切片验证，再决定是否升级；B 是首选升级路径（不需要重写找平）。
```
### 1.2 瀑布 / 自由落体水在模拟里不存在

`z_b` 恒为地面 → **水不能悬空**。原文 §1.8 把瀑布放进"渲染补丁"（竖直面 + 粒子），
但模拟侧仍需回答"落差处水去哪了"。见 §3 决策 2。

### 1.3 "水不是方块"的隐藏成本（触点清单）

好处明确（避免 MC 的双状态物品）。代价是**所有问"这个坐标有什么"的系统都要查两套数据**：

| 系统 | 需要额外处理 |
|---|---|
| DDA 射线（放置/破坏） | 水里的空气能否放方块？放置要不要挤掉水？ |
| 光照 | 水吸收光照（衰减曲线） |
| 音效 | 水下/水面判定 |
| 存档 | chunk 存档多一个水位字段 + 版本号迁移 |
| 渲染 | 独立 translucent 层 + 独立 mesh 调度维度 |
| 物理 | 水不参与碰撞，但浮力/游泳要查水位 |

建议原文补一节"水是独立场的所有触点清单"，避免实现时逐处漏。

## 2. 数值与稳定性

### 2.1 只向最低邻居转移 + 无松弛 → 不收敛

```
现：② 水平：向 η 最低的邻居转移，量 ∝ 高差
缺：① 无死区 ε  → η 差 1e-7 也转移 → 相邻格来回 → 永远到不了 Still
    ② 无 0.5 松弛 → 一次转太多会过冲 → A→B→A 振荡
```

修法见 §4 的 virtual pipes 通量写法（它把"松弛 + 守恒"合成一行）。

### 2.2 耗散与"严格守恒"自相矛盾

```
§1.4 d < d_min → 按 k_seep 递减直至消失      ← 质量汇
§1.6 ② 显式水体严格守恒：只互相转移，不凭空增减  ← 直接矛盾
```

而且 `d < d_min 不扩散` 本身已经把摊开范围界定死了（薄到 d_min 就不再扩），
所以 `k_seep` 其实是**视觉清理**，不是数值必需。二选一写清楚：

- **守恒版**：`d < d_min` → 冻结（保留、不扩散、不耗散）
- **清理版**：`d < d_min` → 按 k_seep 消失，但**明确标注为质量汇**

### 2.3 水位精度：建议整数 0..8

原文 §1.12 已写 `d_max = 8/8`、`d_min = 1/8` —— 这就是 MC 的 0..8 水位。
既然如此，`float depth` 是浪费且有浮点漂移：

```cpp
struct WaterCell {
    uint8_t level;   // 0..8，单位 1/8 格
    uint8_t flags;   // bit0 = isSource, bit1 = inFlowSet
};                   // 2 字节/列，整数守恒，永不漂移
```

收益：守恒是整数相等；转移量天然有最小值；内存减半；存档/传输用整数。

## 3. 必须先定的 5 条决策（含可能的实现路径）

> 这一节写成"决策记录 + 备选路径清单"，而不是"最终答案"：
> 流体是后置项，将来可能花很长时间逐条试，所以每条都保留**升级路径**。

### 3.0 决策之间的依赖关系

```
决策1（同列多水面） ──影响──▶ 决策2（瀑布悬空水）
        │                        │
        └──影响──▶ 决策5（水位精度：分段/分水体后每段的量化）
决策3（卸载边界） ──影响──▶ 存档格式（随 chunk 存 or 全局账本）
决策4（浮力谁算） ──依赖──▶ 决策5（水位查询的精度与语义）
```

**先定 1 和 3（决定数据结构与存档），再定 2/4/5（决定运行期接口）。**

---

### 决策 1：同一列能否有多个水面

完整分析见 **§1.1**（根本原因、三种失败、三条升级路 A/B/C）。
这里只留结论与升级顺序：

| 阶段 | 做法 | 触发条件 |
|---|---|---|
| 1.0 | **每列一个水面**（只留最低连通水面，其余空腔干燥） | 默认 |
| 升级 1 | +`bottomY`（水可以停在台地而不是最低处） | 玩家抱怨"水不下到台地" |
| 升级 2 | **按连通水体分高度场**（每水体一份列→depth 表） | 需要地下湖 / 多层水域 |
| 升级 3 | 逐体素水位（MC 路线） | 需要完全自由的水（含垂直自由落体） |

---

### 决策 2：瀑布 / 自由落体水怎么算

**是什么**：高度场里 `z_b` 恒为地面 → 水不能悬空；但瀑布的水在悬空下落。
模拟必须回答"落差处的水去哪了"。

**为什么必须定**：决定瀑布能否参与玩法（挡实体、推水车、发电），
以及"画的水帘"与"模拟的落点"是否一致。

#### 备选路径

| 方案 | 做法 | 优点 | 代价 | 何时选 |
|---|---|---|---|---|
| **A 纯视觉**（推荐 1.0） | 落差处水在模拟上瞬移到下一格；水帘用竖直面 + 流动纹理 + 粒子 | 最省；与主流非 MC 游戏一致 | 水帘不挡实体、不推水车、不能发电；视觉与模拟可能对不齐 | 1.0 |
| **B 悬空水柱（每列一段）** | 每列额外存"悬空水段"：`{bottomY=-1(悬空), length}` | 瀑布可推实体/发电；落点与视觉一致 | 等于推翻"一列一个水面"（与决策 1 的升级 1/2 纠缠），复杂度跳一档 | 决策 1 升级到 2 之后 |
| **C 下落水用独立轻量粒子场** | 瀑布只作为"抛射粒子 + 落点注水" | 视觉自由（可斜抛/溅射）；模拟侧只需在落点生成水 | 需要粒子→水的质量记账（否则会凭空造水/丢水） | 想要"瀑布发电"但不想改高度场 |
| **D 没有瀑布** | 落差直接断流 | 最省 | 视觉损失大（MC 里瀑布是标志内容） | 不做玩法瀑布时的兜底 |

#### 升级顺序建议

```
A（1.0） → C（要瀑布发电：粒子场 + 落点注水，质量可记） → B（要瀑布参与碰撞/水车）
```

**注意**：C 的关键是"质量记账"——粒子必须携带水量，落到水面时加回水位场，
否则粒子是"免费水"（违反守恒）或"白丢水"。这条必须在实现 C 时先想清楚。

---

### 决策 3：水流出加载区 / chunk 卸载时怎么记账

**是什么**：世界流式加载。加载集内守恒容易，但
① 水从加载区边缘流出（外侧没 chunk）② chunk 被卸载 ③ 走回来 —— 三种情况质量怎么算。

**为什么必须定**：决定**存档格式**（水随 chunk 存？还是全局账本？）与玩家能否看到"水位莫名下降"。

#### 备选路径

| 方案 | 做法 | 优点 | 代价 | 何时选 |
|---|---|---|---|---|
| **A 水汇** | 流出去/卸载的水直接消失 | 最简单 | 玩家能看到边缘水位下降；"走远回来水少了" | 流式半径小、玩家常看到边缘时不可取 |
| **B 边界水库** | 每个边界格维护"外流缓冲"，回来时恢复 | 严格守恒 | 额外状态；看不见的地方无法验证 | 需要严格守恒（联机/回放）时 |
| **C 边界当墙 + 水随 chunk 存档**（推荐 1.0） | 加载集外视为固体墙（不可流入）；水位数据随 chunk 存档 | 不丢水、无可见异常、无额外结构 | "边界有无形的墙"（那里本来没加载，看不见）；存档版本 +1 | 1.0 |
| **D 全局水位账本** | 水位不按 chunk 存，而是全局稀疏表（chunk 坐标 → 水段） | 与流式解耦，边界自然处理 | 存档/加载要按坐标查询；与现有 chunk 存档体系并行维护 | 水需要跨大范围连续（长河/大湖）时 |

#### 与"深渊吸收"的统一

```
· 世界底以下（y < world_min）→ 质量汇（真正的丢失，玩家理解）
· 加载集外            → 墙（不丢水）
· chunk 卸载          → 状态随 chunk 存档（不丢水）
```

#### 升级顺序建议

```
C（1.0） → D（当水需要跨很多 chunk 连续时，例如一条长河贯穿 20 chunks）
```
**C → D 的判据**：如果"水随 chunk 存档"导致"跨 chunk 的水体在边界处水位不连续"（
因为两个 chunk 分别存档、加载顺序不同），就该上 D。

### 决策 4：浮力谁算、怎么送进物理

**是什么**：原则是"模拟全在业务线程，物理只消费力"，但浮力需要水位（在业务线程）。
必须定：力由谁算、怎么跨线程、作用点在哪。

**为什么必须定**：这是**协议改动**（`PhysicsCommand` 现在没有 `ApplyForce`），
会影响已有的增量同步路径。

#### 备选路径

| 方案 | 做法 | 优点 | 代价 | 何时选 |
|---|---|---|---|---|
| **A 业务算 + 批量送力**（推荐） | 业务每 tick 查水位 → 算浮力/阻力/推力 → 一条 `ApplyForces{...}×N` | 符合现有分层；可复用 `PoseHistory` 的"整批一次原子"经验 | 延迟 1 tick（40ms）；需要合并成批 | 1.0 |
| **B 物理读水位快照** | 水位发布成共享快照，物理自己算 | 无延迟；指令零增长 | 违反"物理只消费力"；物理层要懂水位语义 | 浮力需要低延迟（高速入水/跳水）时 |
| **C 物理内置环境力** | 物理里写死"水环境" | 无通信成本 | 玩法耦合进物理层 | 不推荐 |

#### 无论选哪个，都要定的三个细节

```
① 作用点 = 浮心（排水体积中心），不是质心
   只在质心施力 → 船永远不翻也不扶正（一眼假）
② 排水体积：巨体必须查表 V(d)（局部坐标系里的"沿世界竖直方向的淹没高度"），
   不能逐方块遍历；方块破坏 → 标脏 → 增量重算受影响层
③ 玩家游泳是另一条路：CharacterVirtual 吃不到接触力，
   需要"输入改成水中移动模式 + 浮力改写竖直速度"，不能走 ApplyForce
```

#### 升级顺序建议

```
A（1.0：浮力/阻力批量送力） → B（若"高速入水"手感要求高，改成物理读水位） → 
玩家游泳单独实现（与 A/B 无关）
```

### 决策 5：水位精度（存什么数）

**是什么**：`depth` 存 float 还是整数？单位多少？上限多少？决定守恒是否精确、内存、薄水层/河流的量化粗细。

**为什么必须定**：影响存档/网络/渲染/转移量计算，后改成本高。

#### 先厘清一个坑：`d_max` 不是常量 1 格

```
原文 §1.12 写 d_max = 8/8（1 格）
但一个挖了 10 格深的坑，水深就是 10 格（z_b = 坑底，d = 水面到坑底）
→ d_max 实际是"该列能装多深"（地面到下一个空气/地表），可达几十格
```

所以量化单位要么**固定**（配一个足够大的上限），要么**按列容量归一**。

#### 备选路径

| 方案 | 编码 | 精度 | 优点 | 代价 |
|---|---|---|---|---|
| **A uint8 固定单位 1/8 格**（推荐 1.0） | 0..255 → 0..32 格 | 1/8 格（= MC 一格台阶） | 整数守恒；与 MC 直觉一致；2B/列（level+flags） | 32 格以上深度表示不了（但那属于规则水/海沟） |
| **B uint8 按列容量归一** | 0..255 → 0..d_max(列) | d_max/255 | 任意深度都能表示 | 单位随列变化，跨列转移要换算 → 容易算错 |
| **C uint16 固定单位 1/64 格** | 0..65535 → 0..1024 格 | 1/64 格 | 任意深度 + 更细精度 | 4B/列（内存 ×2）；大数值对守恒/复现没额外好处 |
| **D float** | — | 连续 | 直观 | 浮点漂移（0.9999≠1.0）；守恒要 ε 比较；存档浮点；**不推荐** |

#### 一个容易被忽略的关联：精度 ↔ 死区

```
水量被量化成整数单位后，Δη 小于 1 单位时必然转移量为 0
→ 天然给了"死区"，这正是 §2.1 需要的防抖，但会带来"最小流量"：
   薄水层可能永远不流动（看起来"水卡住了"）
→ 需要 d_min 的取值与量化单位一起调（见 §2.2）
```

#### 升级顺序建议

```
A（1.0：1/8 格、上限 32 格） → C（若需要极深水或极细薄水层，改 uint16）
B 不推荐（归一比的成本和出错率高于收益）
D 只在原型/切片阶段临时用（验证算法），正式实现一律改整数
```

#### 与决策 1 升级 3（逐体素）的关系

若将来走逐体素，水位编码应从 `uint8/列` 变成 `uint8/格`，
但"整数单位 + 固定上限"的思路不变（MC 是 4 bit/格）。

| 3 | 卸载边界 | 边界当墙 + 水随 chunk 存档 | 全局水位账本（水跨很多 chunk 连续时） |
| 4 | 浮力 | 业务算 + 批量 ApplyForce | 物理读水位快照（需要低延迟时） |
| 5 | 水位精度 | uint8、单位 1/8 格、上限 32 格 | uint16（需要更深/更细时） |

**1.0 的流体范围（选定上述默认值后）**

```
能做：地表/浅层水池、河流、湖泊、海岸挖坑灌水、水车、船浮力
不做：地下湖、多层水域、瀑布发电、可挡水的瀑布、舱内水位（气室走标量）
```

### 4.1 没有先例的那一样

```
城市天际线 / 水力侵蚀 / 多数地形游戏：地形是 heightmap（无悬空、无洞穴）
→ "每列一个水面"天然正确

我们的世界：体素（洞穴、悬空、可垂直挖）
→ "每列一个水面"是近似，§1.1 的问题就来自这里
```

市面上**没找到**"体素世界 + 每列单一水位场"的成功先例：体素游戏要么走 MC 路线
（逐格方块状态），要么不模拟（Factorio / Satisfactory / 深海迷航）。
**即：这条路走得通，但没人替我们踩过坑**，§3 的决策 1/2 必须自己划。

### 4.2 最值得直接采用的：virtual pipes 的"通量"写法

现设计直接改 `depth`（无通量变量）→ 过冲振荡。
标准做法是每格维护 4 个方向的出流 `f_i`，并用"总量不够就等比缩放"保证守恒与收敛：

```txt
每 tick，每格（活跃集内）：
  // ① 按高差加速出流
  for each 邻居 i:
      Δh = (d + z_b) − (d_i + z_b_i)            // 我的水面高程 − 邻居的
      f_i = max(0, f_i + Δt · A · g · Δh / l)    // A=格面积, l=格距
      if Δh <= ε_flow: f_i = 0                   // ← 死区：防抖

  // ② 关键：只能流走"我有的水"（等比缩放）
  K = min(1, d·Δx² / (Σf_i · Δt + ε))
  f_i *= K

  // ③ 结算
  d -= Σf_i · Δt / Δx²
  邻居 d_j += f_j · Δt / Δx²                     // 由邻居自己的下一步加

  // ④ 顺带产出流速（§1.10 需要的东西）
  v = (Σ f_i 的矢量和) / (d · Δx)                 // 截面积 = 水深 × 格宽
```

第 ② 步那一行等价于"0.5 松弛 + 守恒"：水只会流走它真的有的量，因此**不会过冲**，
收敛有保证；并且 §1.10 想要的"近似流速 = 流量/截面积"直接就有了，不用另算。

若不想引入通量状态，最小替代是：

```
转移量 = clamp(0.5 × (η_self − η_nb), 0, 上限)     // 0.5 松弛
且仅当 Δη > ε_flow 才转移                          // 死区
```

## 7. 性能数字需重算

chunk 是 `CHUNK_SIZE = 16` → **256 列/chunk**：

| 原文 | 实际 |
|---|---|
| §1.12「12 chunks ≈ 1.6 万列」 | 12 × 256 = **3,072 列**（差 5×） |
| §1.11「12 chunks ≈ 320KB」 | 3,072 × 4B = **12KB**（差 27×） |
| §1.11「32 chunks ≈ 2.2MB」 | 8,192 × 4B = **32KB** |

且两个数互相矛盾（1.6 万列 × 4B = 64KB ≠ 320KB）。
另：**"12 chunks 全海 < 1ms/tick"没有意义** —— 全海 = 规则水 = 零模拟。
验收指标应改成**活跃格/秒**，场景取最坏情况（海岸线全挖 + 3 条河 + 多源同时倒水）。

## 8. 最小切片计划（先验证收敛与守恒，不接渲染）

文档再改也回答不了"找平到底收不收敛"。建议先做一个**不接渲染、不接世界生成**的切片：

```
范围：独立 32×32×8 测试区（不走海洋/河流/流式）
数据：uint8 level[32][32] + flags（整数水位，2 字节/列）
逻辑：三态 + 找平（virtual pipes 通量写法，或 0.5 松弛 + ε 死区）+ d_min 冻结
输出：每 10 tick 往日志打一片 ASCII 剖面
```

### 验收用例（都可自动判定）

| # | 用例 | 期望 |
|---|---|---|
| 1 | 单源在平地 | 扩到有限范围后**停止**（不无限摊薄），总量守恒 |
| 2 | 单源在斜面 | 沿坡流到最低处形成平水面，**停止振荡**（这是收敛性的判据） |
| 3 | 挖坑灌水 | 灌到与坑口齐平即停 |
| 4 | 同列两个凹坑 | **主动暴露 §1.1**：观察合并策略是否导致水量凭空消失 |

切片代码 90% 可直接搬进业务线程（纯 CPU，无 Vulkan/Jolt 依赖），**不会白做**。

### 建议顺序

```
1. 先把 §3 的 5 条决策写进原设计文档（半小时）
2. 做最小切片（1~2 天）→ 验证收敛与守恒
3. 切片通过后再谈：接规则海 / 接方块变更 / 接渲染 / 接物理
```

**理由**：规则海 + 实例化 + 河流三块的风险都在"集成"（§5），
而它们的前提是"找平逻辑本身正确" —— 这个前提目前尚未被验证。
