# 模组自由度与责任边界

>状态：**讨论记录**（编号 D28 候选，未并入总表）· 2026-11-07
>关联：《模组架构决策.md》（策略层：通道 / 加载器定位 / 侵入式策略）、《地形模组化边界与Mixin对照.md》（Mixin 实测）、《架构决策-注册表机制.md》
>定位：本文只记**技术论证与 API 分级**。策略决策（WASM 去除、加载器做小、侵入式保留不限制、正式接口做厚）见《模组架构决策.md》，不在此重复。

## 一、四个问题，四句结论

讨论的起点是一句诉求：**「想让模组作者们足够自由，但我不负责」**。这句话拆成四个问题：

1. 能不能在 C++ 里做 Mixin 式自由度？
2. DLL 能不能改引擎内部？开源 + 不限制够不够？
3. 哪些能力该默认给，哪些该有门槛？
4. 加载器与"社区加载器"是什么关系？

四句结论：

- **不在 C++ 复刻 Mixin**——JVM 的三个技术前提，C++ 一个都没有。
- **自由已经存在**——DLL 同进程无隔离，越界是物理事实；要解决的不是"给不给自由"，是"责任怎么落地"。
- **API 按性质分四类**（公开 / 加载器 / 特权 / 内部），不按"我用没用到"分。
- **L0 只做最小 bootstrap，L1 归社区**；L0 的用户是 L1，不是模组作者。

## 二、Mixin 在 JVM 能成立，靠三个前提

| 前提 | 内容 |
|---|---|
| ① 字节码有明确方法边界 | 每个方法是一个独立、可解析的 `Code` 属性，ASM 能精确找到插入点 |
| ② 元数据完整 | 方法签名、局部变量表、注解都在 `.class` 里，注入点可用描述符精确表达 |
| ③ 类加载可拦截 | JVM 允许在字节码进内存之前改写，这是 Mixin 唯一的实现位置 |

C++ 一个都没有：

- **机器码没有方法边界**——只有指令流，没有"这个方法从哪到哪"的结构化信息。
- **编译后元数据全部消失**——签名、变量名、注解都不存在，只剩地址和指令。
- **MSVC 的 LTCG（链接时代码生成）与 `/GL` 会内联小函数**——Release 下想 hook 的函数可能根本没有独立函数体，指令已经混进调用方。

所以二进制 hook（inline detour，内联跳转）用 MinHook / Detours 能做出来，但可靠范围只有 **Debug 构建 + 未被内联的函数**，编译选项一改就失效。

### 2.1 一个反直觉的点

MC 的 Mixin 文化繁荣，是因为 **Mojang 的 API 太窄，而内部代码完全可见、可反编译**，作者没有第二条路。

反过来读就是自由边界的用法：**你越不承诺内部结构，作者越会走 API 提需求**。所以"我不负责"最优雅的实现不是表态，而是不提供越界所需的稳定信息：

- 不导出内部符号（`__declspec(dllexport)` 只给 `modapi/`）
- 不承诺结构体布局（文档连字段偏移都不写）
- 不发布内部头文件给模组作者

守住这三条，作者即使有能力 hook，也拿不到"值得 hook的稳定靶子"。

## 三、DLL 能改引擎内部：四种手段

同一个进程内所有模块共享同一片虚拟地址空间（virtual address space），Windows 在进程内没有隔离。模组拿到引擎的 `World`、`ChunkData`、函数地址，读写它们和读写自己的变量没有区别。

| 深度 | 手段 | 说明 |
|---|---|---|
| 最浅 | 直接读写堆数据 | 知道 `World::chunks_` 的 `unordered_map` 布局，就能拿 `ChunkData::blocks` 直接改方块 |
| 中 | 改代码页 | `VirtualProtect(..., PAGE_EXECUTE_READWRITE)` 把 `.text` 改成可写，再 patch 指令 |
| 深 | inline hook（内联跳转） | 函数开头写 `jmp` 到自己代码再跳回；x64 上必须处理指令边界（Zydis 之类反汇编库），不能盲写 5 字节 |
| 侧 | IAT hook / vtable hook | 改导入地址表把 `vkCreateBuffer` 换成自己的；或拿到对象指针后替换虚表指针 |

**「能」和「稳」是两件事**：ASLR 让每次地址不同，不能硬编码；Release 无符号，只能靠特征码扫描（AOB scan，按字节序列匹配），而编译器版本一变指令序列就变，扫描全废。

越界能力是确定的，越界可靠性是不确定的——后者正好是作者自己该承担的部分。

## 四、开源改变的是难度与责任归属，不是可行性

引擎开源（已定案，见《模组架构决策.md》第八条）。它对"自由 vs 责任"的影响有三层，前两层有利，第三层是陷阱：

1. **作者能精确打击**：布局、函数位置、内部逻辑全可见，hook 从"碰运气"变成"照着源码写"。自由度确实变高。
2. **作者能自己编译**：会出现"魔改客户端"分支（fork 引擎）。那是另一个生态，不算模组，但会分散生态。
3. **陷阱：源码可见会被理解成布局稳定**。作者读了源码，会合理地默认"我有权依赖这个结构"。从此每次重构在他眼里都是"你破坏了我的模组"，而不是"我的模组追不上引擎"——**从"内部结构我做主"变成"必须兼容别人抄来的内部结构"**。

对策：**SDK 与源码分离**。

- 开源发布整个仓库；
- 发给模组作者的 SDK 只含 `modapi/`，不含 `src/`；
- 文档写死一句：**源码可见 ≠ 布局稳定；`modapi/` 之外的任何东西，跨版本不保证。**

## 五、API 四分：公开 / 加载器 / 特权 / 内部

### 5.1 判据

**这个能力是实现正当需求所必需的，还是绕过规则所必需的？**

前者进公开 API（哪怕它很强）；后者进特权 API。

### 5.2 切法：同一件事的三个面

| 同一件事 | 公开做法 | 特权做法 |
|---|---|---|
| 改世界 | 走 `BlockActions` 的裁决（占用、id 合法性、标脏） | 跳过裁决直接写 `ChunkData::blocks` |
| 读世界 | 拷贝出来（`getBlock`、`forEachBlockInAABB`） | 拿 `ChunkData*` 指针自己遍历 |
| 一致性 | 引擎在改动里自动处理（标脏、重建） | 模组自己 `forceRebuildChunk`、自己改脏标记 |

**走裁决、走拷贝、走引擎自动 = 公开；绕过这三样 = 特权。**

### 5.3 四类能力表

| 类型 | 给谁 | 获取方式 | 例子 |
|---|---|---|---|
| **公开 API** | 所有模组 | 默认注入 | `getBlock`、`setBlock`、`subscribe`、`block.list()` |
| **加载器 API** | 只给加载器角色 | 物理位置（`mods/loaders/`）决定 | `loadLibrary`、`registerModRecord`、`beginLoadPhase` |
| **特权 API** | 声明 `unsafe` 的模组（L1 与普通模组同等） | 声明 + build 指纹 | `setBlockRaw`、`getChunkRaw`、`forceFreeze`、`enqueueOnBusinessThread` |
| **内部实现** | 谁都不给 | — | `kMaxApplyPerTick`、`Registry::frozen` 标志、SPSC 队列、`dirtyChunksThisTick_` |

公开 API 候选清单（当前全缺）：

| 能力 | 为什么是正当需求 |
|---|---|
| `world.getBlock(x, y, z)` | 任何模组做事都得先知道周围有什么 |
| `world.forEachBlockInAABB(min, max, fn, user)` | 引擎内部已有（`World.hpp:45-49`），只是没暴露 |
| `world.setBlock(x, y, z, blockId)` | **走裁决**。模组能放方块本身不是越界行为 |
| `world.setInfo()` | 高度范围（`kGenMinY`/`kGenMaxY`）、chunk 尺寸、seed |
| `block.findIdByName` / `block.getInfo(id)` | 反查自己注册的东西 |
| `block.list()` | 列出已注册条目，工具与调试需要 |
| `event.subscribe(type, fn, user)` | 事件总线 |

其中"模组能放方块"必须是公开的：**没有它，事件总线也没有使用场景**——事件的前提是模组能自己产生动作。

特权 API 候选清单：

| 类别 | 代表 | 绕过的是什么 |
|---|---|---|
| 裸写世界 | `setBlockRaw`、`setBlockBatchRaw`、`removeBlockRaw` | `BlockActions` 裁决 |
| 拿内部指针 | `getWorldHandle`、`getChunkRaw`、`getRegistryRaw` | 封装 + 读接口 |
| 跨线程投递 | `enqueueOnBusinessThread`、`enqueueOnWorldgenThread` | 线程安全模型（最易造成数据竞争） |
| 改注册表规则 | `registerBlockWithId`、`removeRegistration(owner)`、`forceFreeze` | id 分配器 + 启动期冻结窗口 |
| 强改渲染一致性 | `forceRebuildChunk`、`patchDirtyFlags` | 引擎自动标脏的约定 |

### 5.4 「我没用到」≠「特权」

这两个轴不相交：一个是使用频率，一个是能力性质。特权 API 按**性质**划（是否绕过规则 / 暴露内部结构），不按使用情况划。

"我没用到"的接口有三种去向：

| 去向 | 判据 | 例子 |
|---|---|---|
| 公开 API | 正当需求，只是暂时没人用 | `forEachBlockInAABB`、`setInfo` |
| 特权 API | 绕过规则或暴露内部结构 | `forceFreeze` |
| 永不开放 | 纯实现机制 | `kMaxApplyPerTick`、`frozen` 标志 |

第三类占多数：这些是**不该被看见的实现**，不是"该开放的接口"。开放了作者就会依赖内部细节（比如依赖"每 tick 只应用 4 列"这个调参），以后每次调参都成了"破坏兼容"。

### 5.5 一条自检问句

> **一个模组作者拿到这个接口，做出来的东西是不是我会认可的游戏内容？**

是 → 公开；不是但确实需要 → 特权；他根本不该知道 → 永久内部。

### 5.6 判据的自我校验（一次修正）

用这条判据回查早期草拟的特权清单，`getBlockRaw(x, y, z)` 属于**正当需求**（读世界），应做成公开的世界读接口，不该塞进特权。这说明判据是可操作的，不是事后找理由。

### 5.7 为什么不能把特权 API 放进公开 API

因为"放进公开 API"改变的不是分类，是**契约**——写进 SDK、写进文档、默认注入，就等于承诺"能用、跨版本稳定、出问题算引擎"，这是文档本身的重量。

四条后果：

1. **责任无法归属**。`setBlockRaw` 摆在公开 API 里，作者会当正规用法；崩了说"你自己负责"说不通。——"我不负责"在公开 API 里是句空话，在特权 API 里是可执行的条款。
2. **捷径成官方推荐，正道就没人走**。特权能力本质都绕过约束（`setBlockRaw` 绕过裁决、`enqueueOnBusinessThread` 绕过线程模型）。公开了等于官方承认"可以绕"，作者会全走捷径，hardness / solid / 状态系统形同虚设。MC 的 Mixin 文化正是这么来的。
3. **后门抑制正式接口演化**。"再加一个 raw 方法"永远比"请设计一个正式的事件/查询接口"省事，需求信号就断了。
4. **兼容义务与审计信号双失**。公开即背兼容债；而分开后能统计"哪些模组声明了 unsafe"。

一句话：**分开不是"分级"，是"分类"——一个是我承诺的，一个是我看见但不承诺的。**

## 六、责任落地的三件套

"我不负责"必须有技术手段支撑，否则在用户眼里就是"引擎崩了"，责任还是回到引擎作者身上。

| # | 机制 | 作用 |
|---|---|---|
| ① | **清单声明**（`mod.json` 里 `unsafe: true` / `hooks: [...]`） | 让越界行为可识别 |
| ② | **崩溃归因**：Vectored Exception Handler（向量化异常处理）+ `GetModuleHandleEx(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS)` | 把崩溃地址映射回所属 DLL，日志写"由 `xxx.dll` 导致"。**这一条最关键** |
| ③ | **版本指纹拒绝**：引擎 build id + 模组清单声明依赖哪个 build | 防止作者以为 hook 能跨版本 |

### 6.1 声明不是许可，是自证

设计要反过来：如果把声明做成"安检门"（声明了就放行、不声明就拦截），模组一定选"不声明"，结果两头空。

正确形态：**默认放行，声明的作用是自证。**

- 声明了 `unsafe`：加载时打醒目日志，崩溃时优先怀疑它，日志写它的名字。
- 没声明但越界了：归因工具救不了（崩溃可能发生在被改写的引擎代码里），日志只能是"未知"。

于是**让"不声明"比"声明"更难受**，而不是让"不声明"被拦住。绕过的代价不是被阻止，是**失去保护**。

### 6.2 默认应该关

一旦把越界当常规路径，作者会立刻依赖，引擎作者就被迫在每次重构时兼容它——自由度反而变成约束。所以默认拒绝，`unsafe` 显式 opt-in。

## 七、特权 API 的承诺边界

三句话：

- **不承诺语义**：行为、时机、副作用、跨版本的"用法"都可能变。函数本身还得维护（它在引擎里，重构时签名会被动跟着改），能承诺的下限只是"编得过、调得到"。
- **不承诺说明**：更新不主动说改了什么。这条成立的前提是**开源**（作者能自己看 diff 适配）；不开源又不说明，就不是"作者自己承担"，是单方面毁约。
- **承诺归因**：它崩了，日志里能写出它的名字。

### 7.1 一个反噬

特权 API 存在的唯一意义是"让越界变成可观测的"。如果它经常坏、语义反复变，作者会退回"特征码扫描 + 硬 hook"——那条路不需要学任何约定，也就不需要登记。

**特权 API 越不稳定，作者越绕开它；作者越绕开它，"不负责"越立不住。**

所以"不管"有一个下限：它得稳定到作者愿意用。不是保证它好用，只是不能坏到被嫌弃。

对作者的承诺只有一句：**我不保证它好用，我保证它看得见。**

## 八、加载器分层：L0 与 L1

| 层 | 谁 | 在哪 | 能决定什么 |
|---|---|---|---|
| **L0** | 内置最小 bootstrap | EXE 内 | "哪些 DLL 能进"——分发 `ModApi`、记录归因 |
| **L1** | 社区加载器 | `mods/loaders/*.dll` | "它自己管的模组能进"——但每个 DLL 都要走 L0 的 `loadLibrary` |
| **L2** | L1 管的模组 | L1 指定目录 | 什么都不决定 |

深度就是权限边界：L0 决定根，L1 决定子树，L2 什么都不能决定。

### 8.1 L0 必须自己做的（碰引擎内部，下放不了）

1. 找到 DLL（扫描目录）
2. `LoadLibrary`
3. 取 `CreateMod` / `DestroyMod`
4. 分发 `ModApi` 指针
5. 驱动 `onLoad` / `onUnload`
6. 记录 DLL → 地址范围（归因表）
7. 版本指纹不匹配就拒绝

### 8.2 L1 才有资格做的

发现策略（本地 / 压缩包 / 网络）、依赖解析、拓扑排序、版本协商、同名方块冲突的**呈现**、配置 UI、启用禁用、包格式与签名、热重载。

### 8.3 L0 永久不做的四件事

依赖解析、包格式、UI、热重载。

这四件是加载器产品的一部分，不是引擎机制的一部分。**这个"永远不做"的决心，才是 L1 存在的空间**——如果是"我以后自己加"，L1 永远没有位置。

### 8.4 三条硬约束

1. **目录归属唯一**：L0 管 `mods/*.dll`，L1 管它自己的目录，两者不能管同一个目录，否则"哪个加载器该加载它"没有答案，加载顺序与归因表直接打架（而且不报错，只是行为随机）。
2. **深度限 2**：L1 不能再加载出 L1。
3. **L0 不做成可替换的 DLL**：一旦 L0 本身是 DLL，就有鸡生蛋问题——谁来保证这个加载器本身能加载、能跑？L0 永远留在 EXE，保持最小。

### 8.5 加载器 API 是"身份"，不是"权限"

L1 本来就能 `LoadLibrary` 任意 DLL，限制它调公开 API 没有意义。给它 `LoaderApi` 的实际含义是：**引擎承认"你是加载器"，因此对你开放驱动其他模组的原语，并把你的加载行为纳入归因表。**

集合关系：

```
普通模组 ⊂ 公开 API（+特权）
L1       = 公开 API + 加载器 API（+特权）
```

不是"L1 用公开 API"，而是"L1 是特权级的模组，公开 API 它照用，只是多了驱动别人的原语"。

### 8.6 走正门：`ModApi` 只由 `loadLibrary` 分发

```c
struct LoaderApi {
    bool  (*loadLibrary)(const char* path, void** out_handle);
    void* (*getModEntryPoint)(void* handle, const char* symbol);
    bool  (*unloadLibrary)(void* handle);
    const ModApi* (*getEngineApi)(void);
    bool  (*registerModRecord)(const char* dllName, const char* modId,
                               bool unsafeDeclared, const char* buildId);
    bool  (*beginLoadPhase)(void);
    bool  (*endLoadPhase)(void);
};
```

`loadLibrary` 由引擎实现，`ModApi` 指针只能通过它分发。加载器可以自己 `LoadLibrary`，但那样拿不到 API。

这不是限制，是**把能力分发做出唯一入口**：走正门拿得到 API；走侧门能加载，但拿不到 API。于是"哪个 DLL 是引擎亲自加载的"这个信息永远完整，崩溃归因永远能走到具体模块。

**前提是走正门必须比走侧门省事**：正门给 `ModApi`（不用自己 `GetProcAddress` 找 `g_api`）、给归因（崩了有人管）、给特权（声明 `unsafe` 后有 `UnsafeApi`）；侧门什么都没有，除了自由。如果 L1 作者觉得自己 `LoadLibrary` 更简单，归因表就只剩内置那两个 DLL，其余全是"未知"。

### 8.7 id 分配顺序的裁量权必须留在 L0

方块 id 会写进存档，加载顺序一变 id 就漂移。所以 L0 定义 phase（阶段）：

```
builtin → loader → normal
```

L1 只能在某个 phase 内部排序，不能跨 phase。这一条正好把 `blocks.dll` 必须字典序最前才能保证 id 1~6 的隐患，从"碰运气"变成"声明 + 阶段保证"。

### 8.8 冲突处理：机制在 L0，呈现给 L1

"两个模组注册同名方块"怎么处理，L0 的默认策略必须统一（建议拒绝 + 报错）；"怎么展示给用户"才归 L1。否则同一份模组装在不同加载器里行为不同，作者没法调试。

### 8.9 社区加载器的意义

它不"帮你加载模组"（那是 L0 的活），而是**把最小机制产品化**。类比：JDK 有 `ClassLoader`，但没人用它直接管依赖，Maven / Gradle 才在上面做产品。L0 是 `ClassLoader`，L1 是 Maven。

代价是碎片化：不同 L1 各自成生态，模组不能跨 L1 使用（除非只依赖 `modapi/`）。换来的是责任外移——依赖冲突、版本混乱、加载失败，这些最费精力的事都归加载器作者。

## 九、WorldApi：读世界的定位与一个坑

### 9.1 它是什么

给模组"看世界"的三个函数，属**公开 API**：

| 函数 | 作用 | 返回 |
|---|---|---|
| `getBlock(x, y, z, &out)` | 读一个坐标 | 三态：有方块 / 是空气 / 该 chunk 未加载 |
| `forEachBlockInAABB(min, max, fn, user)` | 遍历区域内方块 | 回调给出坐标与 id |
| `getWorldInfo(&out)` | 读世界属性 | 高度范围、chunk 尺寸、seed |

`getBlock` 建议返回枚举而不是 `bool`：`false` 混着"这里是空气"和"这块没加载"，而模组需要区分（往空气里放块 vs 查询远处未加载区域）。

### 9.2 为什么它是正当需求

没有它，下面这些模组都写不出来：

- **环境感知型**：检测周围有什么，据此改变自己
- **结构生成型**：遍历区域，在不冲突的位置放置方块
- **边界感知型**：知道自己能操作的范围（`kGenMinY=0` 到 `kGenMaxY=63`）

### 9.3 引擎内部已经全都有，不用新写

- `World::findBlock(p)` → `World.cpp:105-119`，已加锁，返回 `optional<Block>`
- `World::forEachBlockInAABB(min, max, fn)` → `World.cpp:126-144`
- `kGenMinY` / `kGenMaxY` / `CHUNK_SIZE` / `WorldPreset::seed`

### 9.4 必须解决的一个坑：持锁回调

`forEachBlockInAABB` 是**持锁遍历、在锁内调用 `fn`**（`World.cpp:133-143`）。而 `findBlock` 的注释已经写明（`World.cpp:108-110`）：

> `blocksMutex_` 是不可重入的 `std::mutex`，持有本锁的函数内部不得再调用本函数，否则自死锁。

这话对引擎内部成立（内部代码遵守纪律），但**一旦把 `fn` 换成模组回调，纪律就失效**：作者不知道这条，很可能在回调里调 `getBlock` 查邻居，当场死锁——而且是持锁死锁，整个业务线程卡死。

所以暴露时必须改：**先遍历、拷贝出区域内的方块列表，释放锁后再回调模组**。代价是区域大小的临时内存（16³ 区域最多 4096 × 20 字节 ≈ 80 KB），换来"锁内绝不执行外部代码"。这是正确做法，不是性能妥协。

### 9.5 归属与版本

`ModApi` 末尾追加 `WorldApi world;`，`kEngineApiVersion` 3 → 4。追加不改老模组偏移（`IMod.hpp:11-12`），但版本号要让模组能检查"这个接口到底有没有"。

### 9.6 世界读与事件是成对的

模组现在只有 `onLoad` / `onUnload`；`onLoad` 执行时世界还没生成。所以即使给了 `getBlock`，也没有"什么时候调"的地方。

- **世界读 = 能力**
- **事件 = 时机**
- 只有能力没时机，用不上；只有时机没能力，干不了事。

所以两者要成对做。顺序上可先写 API、后接时机，但**事件总线的第一个事件不该是"方块放置"，而是"tick"**——"我每隔一会儿能跑一次"是所有模组最底层的运行需求；有了 tick，世界读立刻可用，方块放置只是第二个事件照着抄。

## 十、明确不做

| 项 | 理由 |
|---|---|
| C++ 复刻 Mixin | 三个技术前提一个都没有；可靠范围仅 Debug + 未内联函数 |
| 现在实装 `UnsafeApi` | 公开 API 还基本为零，没有正常用法就谈不上"绕过"；现在加就是死代码 |
| 在 `ModApi` 里提前塞空字段 | 无使用者就是死代码；追加纪律保证将来能加 |
| L0 做依赖解析 / 包格式 / UI / 热重载 | 永久归 L1，否则 L1 没有存在空间 |
| 按角色限制特权 API | 技术上分不清（L1 也可同时是普通模组）；按角色限制会制造"自称加载器"的绕道漏洞；归因按模块不按角色 |
