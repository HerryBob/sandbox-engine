# 09 模组化边界（决策稿）

**状态：决策稿 —— 只定边界，不写代码。**
**目的：接 Jolt 之前把「哪些能力必须引擎提供、哪些内容留给模组、ABI 怎么长」定下来。**

> 这份文档解决一个顺序问题：七维度是「先做成引擎功能再抽成模组」，还是「一开始就做成模组」。
> 答案见 §八：**都不是**，先用一个纵向切片把 API 打磨出来，再顺着推。

---

## 一、三条硬结论

### ① 跨模组网络必须归引擎

03 动力、04 传动、05 推力、06 滚动、08 信号 都消费同一张「旋转网络」。

如果每个模组自己维护网络，就会出现：**A 模组的动力块驱动不了 B 模组的传动杆**。
所以网络（节点注册 / 边注册 / 统一传播 / 一次性提交）必须是**引擎的共享服务**，模组只声明
「我是哪种节点、参数是什么」。

→ **种子方块可以模组化，网络不能。**

### ② 物理 API 的边界必须在接 Jolt 时定形

05/06/07 都要写物理：读刚体、加力（**带作用点**）、建约束、声明圆柱形状。
一旦这些东西以「引擎内部接口」的形态做出来，以后开放给模组就要重写门面。

→ 接 Jolt 时，`PhysicsWorld` 的公开面**按 C ABI 的形状设计**（先用引擎内部，暂不导出）。
导出是零成本；反过来抽取是重写。

### ③ 引擎代码里不得出现任何具体方块名 / id 语义

这是《索引》第三条原则「不出特殊方块」的技术含义。
引擎只认「节点语义」（旋转源 / 旋转传递 / 旋转消费 / 信号源…），谁是哪一种由模组的注册数据决定。

→ 如果先做「引擎内的七维度」，引擎必然认识「动力块」这个具体方块，抽出来时要把这些痕迹全拆掉。

## 二、现状：能力面盘点

模组当前能调的全部能力（核实自 `modapi/*.h`）：

| API | 函数 | 性质 |
|---|---|---|
| `BlockApi` | `registerBlock(def)` | 静态注册 |
| `WorldApi` | `getBlock` / `forEachBlockInAABB` / `getWorldInfo` | **只读查询** |
| `EntityApi` | `registerEntity(def)` + `onAnimate(user, dt, speed, …)` | 注册 + 每帧回调 |
| `NoiseApi` | `registerNoise(provider)` | 地形生成 |
| `ModVtbl` | `onLoad` / `onUnload` / `destroy` | 生命周期 |

**结论：现在是「静态注册 + 只读查询」型，而七个维度全部是「每 tick 主动驱动 + 写物理」型。差一个数量级 —— 但差的是能力面，不是基础设施。**

基础设施已经在跑：纯 C ABI（`CreateModC` 单导出）、依赖排序、按来源回滚、卸载闭环、三个内置模组。

## 三、逐维度缺口

| 维度 | 模组需要什么 | 现在有吗 |
|---|---|---|
| 01 底座 | 质量 + **体积** + 三层属性 | ⚠️ 有 `mass`，**没有 `volume`**；三层属性机制没有 |
| 03 动力 | 每 tick 驱动 + 写刚体角速度 | ❌ 无 tick 回调、无物理 API |
| 04 传动 | 每 tick 建图传播 + 读相邻方块 + 施加角速度 | ⚠️ 能读方块；❌ 无 tick、无物理 |
| 05 推力 | 每 tick 读转速 → 给刚体**任意点**加力 | ❌ 无物理 API |
| 06 滚动 | 圆柱形状 + 切向力 | ❌ 无形状系统、无物理 API |
| 07 约束 | 创建铰链 | ❌ 无物理 API |
| 08 信号 | 图传播 + 读写节点值 + 读玩家输入 | ❌ 无 tick、无自定义状态、无输入 API |

| `ModApi` 末尾加 `const ModTickApi* tick;` | 同上 | 同上 |

## 五、纵向切片：03 动力 + 05 推力

**为什么选这两个**：

| 理由 | 说明 |
|---|---|
| 最小闭环 | 动力块（无 → 旋转）+ 推进器（旋转 → 力）→ 打通「网络 + 物理 + tick」三层 |
| 不碰形状系统 | 05 只需要 `AddForce(带作用点)`，Jolt 现成 |
| 不碰多刚体 | 绕开 07 那个「单刚体 vs 多刚体」的争议 |
| 失败成本低 | 两个方块，写错重写也只两个 |

**切片要新增的 API 面**：§四表 1 里标 ✅ 的 6 项 = 6~8 个函数指针 + 1 个字段。

**切片验收（三条，与 Jolt v1 的三条并列）**：

1. 动力块 + 推进器装在同一个结构上，推进器按转速产生推力
2. 推进器装偏（不在质心正后方）时结构**会偏航**（验证「力可作用在任意点」）
3. 卸载模组后，结构失去动力（验证「按来源回滚」对物理也成立）

**模组放在哪**：`mods_src/kinetics/`（与 `blocks` / `noise` / `player_entity` 并列）。
**已定（2026-11-23）**：切片模组的目录名就用 `kinetics/`，后续维度模组沿用同一命名风格
（动词/领域名，小写下划线按需）。

## 六、三条实现纪律

### ① 批量回调，不是逐方块回调

模组是 DLL，跨边界调用有成本。逐方块回调在 1000 个动力块时就是 1000 次跨 DLL 调用。

```c
// ❌ 每方块一次
int32_t (*onTickBlock)(void* host, uint16_t blockId, const void* params);

// ✅ 批量：一次调用处理一批节点
int32_t (*solveNodes)(void* host, const ModNodeIn* in, uint32_t count, ModNodeOut* out);
```

### ② 物理 API 只出现「结构 id」，不出现 Jolt

```c
// ✅
int32_t (*addForce)(void* host, int32_t structureId,
                    float fx, float fy, float fz,
                    float px, float py, float pz);   // p = 作用点
// ❌ 禁止：JPH::BodyID / JPH::Vec3 / JPH::Shape 的任何痕迹
```

这就是 Jolt 文档里「不得泄漏任何 Jolt 类型到桥」的同一条约束，延伸到 C ABI。

### ③ 求解与提交分成两个相位

08 文档写死「算完所有输入再一次性提交」，否则对外输出瞬时 0（推进器停一帧、灯闪一下）。

引擎必须提供：

```
求解相位：模组只读世界 + 写 out[]（不写世界）
提交相位：引擎统一把 out[] 写入网络与物理（唯一写者）
```

## 七、与 Jolt 的衔接：门面设计检查表

接 Jolt 时，`PhysicsWorld` 的公开面要能「翻译成 C ABI 而不失真」，逐条自检：

| 检查项 | 通过标准 |
|---|---|
| 力的作用点 | 门面有 `addForce(id, f, pos)`，而不只是 `addForce(id, f)` |
| 结构 id 稳定 | 引擎内部的 body 句柄可以被映射成 `int32_t` 且**不暴露** |
| 约束可建可拆 | `createHinge` / `destroyConstraint` 成对存在 |
| 形状可声明 | 至少能表达「圆柱/胶囊」（06 的硬约束） |
| 无 Jolt 类型外泄 | `Mod*Api` 里 grep 不到 `JPH` |

**⚠️ 一个必须先解决的结构冲突**（见《未来方向-物理内核替换为Jolt》§六 vs 《07-约束》）：

```
Jolt v1：复合体 = MutableCompoundShape       → 一个结构 = 单个刚体
07 约束：「必须是真铰链」                     → 需要多刚体 + 约束
```

**建议**：Jolt v1 就把 `PhysicsState` 按「一个结构 = 可拆成多个刚体 + 约束表」建
（1.0 可以先只用一个刚体），否则 07 上线时要推翻刚体模型，连带 `contraptionId`、
快照协议、渲染 bodyMesh 全改。

`PhysicsBridge` 的单槽位（B103）、`VulkanContext` 的请求覆盖（B135）都是这么来的。

**切片路线总工作量 ≈1.1×**，且只有 1 个维度需要返工。

### 第 1 条的展开：多刚体 + 约束表是什么

| | 现在（单刚体） | 多刚体 + 约束表 |
|---|---|---|
| 一个结构 | 一个 `RigidBody` | N 个 `PhysicsBody` |
| 结构内相对运动 | 不可能 | 关节处可转 |
| `contraptionId` | = 刚体 id | = **结构 id**（下面挂 N 个 body） |
| 位姿协议 | `BodyPose{contraptionId, 一个位姿}` | 每个 body 一条（带 bodyId） |
| 渲染 | 一个结构一个 mesh + push constant 平移 | 每个 body 一个 mesh，各自变换 |
| 07 关节 | ❌ 必须推翻重做 | ✅ 天然支持 |

```cpp
struct PhysicsBody       { int bodyId; int structureId; 位姿; std::vector<Block> blocks; };
struct PhysicsConstraint { int id; int bodyA, bodyB; Axis axis; Vec3 anchorA, anchorB;
                           float minAngle, maxAngle, damping; };
struct PhysicsState      { std::vector<PhysicsBody> bodies;
                           std::vector<PhysicsConstraint> constraints;          // ← 表
                           std::unordered_map<int, std::vector<int>> structureBodies; };
```

「表」的含义：**约束是数据**（可增删、可存档、可被模组创建），不是代码里的固定关系。
1.0 可以只用一个刚体（表为空），但**数据结构按多刚体建** —— 这样 07 上线时零改动。

### 第 2 条的展开：三层属性（**已定：暂不做**）

> **决定（2026-11-23）**：暂不引入三层属性系统。属性就是扁平字段，
> 由模组代码在 `registerBlock` 时逐个填写。理由：目前方块数量少，
> 数据表 + 解析器的收益抵不上复杂度。

将来若要引入，形态是这张表（先记着，不动手）：

| 层 | 作用 | 例子 |
|---|---|---|
| selector | 命中哪些方块 | `tag=stone` / `block=obsidian` / `block=slab, state=half=bottom` |
| priority | 多条命中时谁赢 | 数字越大越优先（默认 < 材质 < 具体方块 < 状态） |
| overrides | 命中后改哪些属性（其余继承） | `{mass: 2.6}` / `{volume: 0.5}` |

解析：**收集命中 → 按 priority 升序 → 依次合并 overrides → 得到最终属性**（密度 = 质量÷体积，只读派生）。

**触发条件**（满足任一再重新评估）：
1. 方块总数超过 ~100 个，出现"每个方块重复填同样的质量"
2. block state 落地（`BlockType` → state id），属性要按 state 分叉
3. 需要第三方模组修改别人方块的默认属性

届时的兼容路径已经留好：**现行 `ModBlockDef` 的扁平字段就是"最低优先级的那一层默认值"**，
已有模组不改也能跑。
