MinecraftGame2 · 引擎架构对照

Minecraft 开发路径
能给我们的引擎什么提示

MC 的架构演进史是一部"先能玩、后还债"的实录：chunk 先行、服务端权威、渲染长期被拖成短板、数据格式重构代价巨大。下面把每个关键阶段映射到 MinecraftGame2 的对应决策与下一步。

chunk / 权威 已做对 渲染深化 正当其时 数据格式 前车之鉴

01MC 关键阶段 → 我们的映射

2009Classic
MC：Notch 原型，Java Applet，glBegin 立即模式逐面画方块，无 chunk、世界极小。
→ 我们：固定 2 方块 mesh（48 顶点/72 索引）= MC 的"最小可玩"起步，路线一致。
2010Alpha
MC：无限世界 + chunk（16×16×高）动态生成/卸载，区块成为一切的地基。
→ 我们：chunk 先行（16³ 稀疏 + 脏标记 + 变更事件流），起点比 MC 当年更高。
20111.0
MC：正式版 + 多人兴起，服务端权威成形（防作弊 / 一致性）。
→ 我们：业务权威（裁决唯一权威 + 指令/回执可追踪），与 MC 服务端权威同思想。
20121.2
MC：Anvil 存档格式（region 32×32 chunk、zlib、1KB 对齐）+ 世界高度 128 → 256。
→ 提醒：存档格式是"改起来最贵的"——我们尚无存档，将来设计时早定结构。
20141.8
MC：渲染 VBO 化——每 chunk 一个批量缓冲，draw call 从"每面一次"降到"每 chunk 一次"。
→ 我们：渲染线程深化 = 同一方向（消费脏 chunk 重建网格 → 合并/实例化）。
20181.13
MC：扁平化——方块 ID 从硬编码数字 → 命名空间字符串，为数据驱动/模组铺路，迁移代价巨大。
→ 提醒：我们的 BlockType 是枚举数字——早期把方块定义做成可扩展注册表，省一次大重构。
20211.18
MC：世界高度 384（Y=-64..320）——chunk 结构 + 存档格式 + 光照联动修改。
→ 提醒：我们的 16³ chunk 若未来扩展高度，注意结构与存档的联动成本。
2020sSodium
MC：社区模组用现代渲染器重写 vanilla 渲染，帧率翻倍——渲染是 MC 拖得最久的短板（vanilla 十年未大重构）。
→ 我们：渲染线程深化正当其时，别拖到架构定型后再返工。

03三条硬提示

1

chunk / 权威先行已做对

MC 证明这两件事是地基。我们起点更高：稀疏 chunk + 事件流 + 指令/回执可追踪。

2

渲染别拖

MC 十年渲染债被 Sodium 一次还清。我们正在渲染深化阶段，正当其时——这是每帧都跑的层。

3

数据格式早设计

1.13 扁平化与 1.18 高度扩展都是"改起来最贵"的。BlockType 注册表化 + 存档结构值得前瞻。

与 ARCHITECTURE.md 衔接：本文是对照视图，架构决策全文见 docs/ARCHITECTURE.md（15 条决策 + 8 个踩坑记录 + 路线图）。

下一步（建议顺序）：① 渲染线程深化（伪渲染 → 真实 chunk 网格重建）→ ② 动态方块渲染（网格重建 / GPU 实例化）→ ③ 优化里程碑（mipmap、面剔除、网格合并，遇瓶颈再学）→ ④ 呈现模式与帧率控制（与渲染深化一起做）。
